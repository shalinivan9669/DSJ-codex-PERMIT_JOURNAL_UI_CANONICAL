## Ресурсные защиты

10 000 людей / 50 000 назначений и документов — технические защитные пороги текущей обработки в памяти, не нормативный размер группы и не обещание измеренной производительности на верхнем пороге. Пример пользователя 400 не стал новым пределом. Параллельно действуют JSON 32 МиБ, загрузка XLSX/CSV/TSV 5 МиБ, ограничение распакованного XLSX 30 МиБ / 2000 ZIP entries, 100 столбцов, ограничения размеров полей и файлов renderer. При превышении приложение сообщает о техническом объёме и сохраняет состав; совет вручную делить обычный список удалён из затронутых сообщений.

В импорте найден и исправлен дополнительный реальный барьер: Python повторял весь список на stdout и превышал 2 МиБ канала метаданных. Полный список по-прежнему находится в выходном JSON; stdout теперь содержит только count/canApply и метаданные файла. Защита канала stdout не увеличена.

Браузерный прогон выявил ещё один отдельный предел: 1203 плана передавались Python одним preflight-вызовом, который корректно отклонял более 1000. Новый `layout-preflight.ts` сохраняет этот Python guard и проверку каждого макета; собирает исходные индексы ошибок из ограниченных пакетов. На любой ошибке renderer или неполном ответе весь запрос остаётся непроверенным; новые пакеты после ошибки не стартуют, текущие завершаются. Cache, fingerprint, права и проверка неизменности редакции сохранены. API typecheck / целевой ESLint PASS; 3/3 теста проверяют все 1203 идентичности, ошибки после границ (501, 1001, 1202), конкуренцию ≤4 и отказ на неполном/неверном результате. Лог `.runtime/layout-preflight-unit.log`.

Измерения настоящего Python preflight текущих активных форм (не PDF и не оценка скорости production): 5 карточек БиОТ — 1.005 с, ПТМ — 0.445 с, ПБ — 1.023 с; один протокол на 400 людей — 22.535 / 24.670 / 21.481 с соответственно. Поэтому увеличение одного Python batch до 50 000 не использовалось. Логи `.runtime/preflight-timing.log`, `.runtime/preflight-group-timing.log`; итоговое время полного браузерного запроса фиксируется отдельно.

Отдельные пределы в приглашениях портала и подборе получателей сервисных операций (1000) и общих списках истории не менялись: они не ограничивают проверенный импорт 400 в одной заявке. Нельзя описывать продукт как полностью безлимитный.

## Реальный браузерный сценарий

Исходник: `apps/web/e2e/operator-minimal-actions-400-live.spec.ts`; входной XLSX генерируется через `scripts/verification/generate-import-scale-fixture.py` по короткому локальному пути `.runtime/excel-400-<uuid>.xlsx`, точная копия сохраняется в результатах Playwright. В книге действительно 400 строк и 12 столбцов неизвестных персональных сведений; даты, часы, результаты и программы через API не подставляются. ПТМ и ПБ требуют фактическую длительность: в синтетическом сценарии оператор вводит по 16 часов один раз на курс через общий UI, система не угадывает их из названия.

Сценарий создаёт одну COMPANY-заявку через UI, вводит новое название компании один раз, выбирает XLSX, применяет все 400 строк, назначает БиОТ/ПТМ/ПБ по одному общему действию, вводит неизвестные часы один раз на курс, ждёт автосохранения, перезагружает, передаёт полный состав директору и согласует одной командой. Проверяет ровно 1203 документа (1200 личных + 3 общих) и неизменность items/events после решения директора. `excel-400-saved.json` фиксирует состав сразу после перезагрузки даже при последующей ошибке; `excel-400-readback.json` создаётся только после подтверждённого решения директора.
