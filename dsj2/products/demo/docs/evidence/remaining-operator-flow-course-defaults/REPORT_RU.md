Порядок разрешения значений: `COURSE` → настройки центра → пользовательский набор → общие поля заявки → событие → персональное `MANUAL` / `IMPORTED` / `CLEARED`. Происхождение встроенной программы хранится как `COURSE`. Прежний нестандартный непустой текст рядом с устаревшим автоматическим маркером сохраняется как ручной. Явная очистка и языковые исключения не заменяются встроенными значениями. Полученные ранее неизменяемые снимки не проходят повторное применение defaults.

`GET /training-topics` возвращает встроенную и ранее сохранённые темы своего tenant нужного направления; БиОТ дополнительно разделён на рабочего и ИТР. В ответ входят только программа, KZ и дисциплины ПС. Результаты, оценки, даты и основания в справочник не включаются. Выбор темы в интерфейсе показывает заменяемую общую программу и KZ перед применением; персональные ручные исключения сохраняются.

Результат подтверждается как отдельный фактический `outcome.status` с источником. Положительные документы LIVE_V1 планируются только для `PASSED`. UNKNOWN/FAILED/ABSENT очищают прежние положительные литералы в индивидуальном и групповом mapper. Реальный ручной балл, например `30/100`, сохраняется в данных и печатается с отрицательным статусом: `Не сдал; 30/100` / `Тапсырмады; 30/100`. Готовая оценка `Хорошо` из старого макета не используется как факт нового человека. Поля фактической проверки знаний и прокторинга ИТР сохраняются.

ПС допускает отдельные необязательные `professionRu/Kz` и `psQualificationRu/Kz`. Удостоверение использует профессию; свидетельство и протокол с исходной колонкой «Присвоенная квалификация, разряд» — отдельно заданную квалификацию, затем профессию, затем общее значение строки. Основная должность человека в смешанной многокурсовой заявке сохраняется. Данные связанного комплекта переживают JSON reload и не попадают в другой курс. Языковые варианты применяются отдельно; пустое исключение возвращает общее значение. Эта привязка протокола уточнена после визуального просмотра фактически созданного PDF.

Поздняя проверка внешних предложений выявила ошибку границы редакций: портал продолжал показывать прежнюю согласованную область после частной правки ожидающего человека, а отправка требовала одновременно эту опубликованную и новую рабочую revision. `submitEmployerProposal` теперь проверяет переданную опубликованную revision и неизменность всей выбранной согласованной области по `approvalScopeValue`; в PortalProposal сохраняется текущая рабочая revision для обязательного CAS при рассмотрении. В неизменяемом аудите отправки закрепляются точная опубликованная область и отдельно существовавшая оформленная история. `resolveEmployerProposal` использует этот источник; повтор создаётся только из оформленного состава, доступного текущему представителю, без ожидающих людей/курсов и без согласованного сотрудника другого работодателя. Данные для доказательства исходного scopeHash восстанавливаются из сохранённого согласованного payload, а разрешённый внешний DTO остаётся явным whitelist. `portal-proposal-source-v4.log`: **10 PASS, 0 FAIL/SKIP, exit 0**, 7.921 секунды; отдельный `portal-proposal-source-v5.log`: **1 PASS, 0 FAIL/SKIP, exit 0**, 2.730 секунды, добавлена явная защита изменённой выбранной области. Сохранены исходные отрицательные v1–v3, их причины относятся к точному комплекту PB, правильной индивидуальной принадлежности artifact и выбранным данным следующего согласованного выпуска; проверки не удалены.

Для уже существовавших PENDING PortalProposal с прежним аудитом без `publishedDraft` добавлен узкий `recoverLegacyPortalProposalSource`. Он читает только исторические SAVE-источники и неизменяемые выпуски своего tenant/request, существовавшие не позже `PortalProposal.createdAt` и с исходной revision не выше сохранённого CAS. Факт прежнего APPROVE доказывается датированным `ProposalDecision` с точным proposalHash либо связанным `CHANGE_APPROVED` audit; нынешний статус APPROVED или время отправки на согласование не заменяют время решения директора. Область проецируется только по сохранённым назначениям и проверяется по scopeHash; затем её выбранные значения должны совпадать с текущей рабочей областью. Частный полный рабочий payload и текущий FINALIZED статус не являются fallback-источником восстановления. Права представителя проверяются повторно под блокировкой membership: работодатель, разрешённые строки, активность, срок и нужное разрешение. Успешное принятие старого предложения сохраняет тот же ID и фиксирует отдельный неизменяемый `EMPLOYER_PROPOSAL_SOURCE_RECOVERED` с ID исторического согласования/выпусков и хешами. Повреждённый современный `publishedDraft` не переводится в режим старой записи.
