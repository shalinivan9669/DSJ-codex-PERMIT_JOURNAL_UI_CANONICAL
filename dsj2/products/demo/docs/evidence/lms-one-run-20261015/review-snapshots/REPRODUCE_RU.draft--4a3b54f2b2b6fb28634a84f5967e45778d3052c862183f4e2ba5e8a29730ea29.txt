2. ПОДГОТОВКА И ЗАПУСК

Если зависимости ещё не установлены:
  pnpm install --frozen-lockfile

Только после проверки, что выбран именно описанный собственный тестовый PostgreSQL:
  pnpm db:deploy

Применяются 25 миграций, включая две аддитивные LMS-миграции 202610150023_lms_foundation и 202610150024_lms_result_revisions. Не использовать db push, legacy seed, reset или clean. Для повторения установки с нуля брать отдельную новую demo_test* БД и новое хранилище; точная исполненная процедура с проверками SHA находится в STORAGE_ACCEPTANCE.json. Чистая установка зависимостей проверена отдельно без прежнего node_modules: CLEAN_INSTALL_02.json.

Для существующего центра после миграций добавить три текущие формы LMS отдельной явной командой, указав его проверенный tenant UUID:
  pnpm exec tsx --tsconfig tsconfig.base.json scripts/maintenance/register-lms-templates.ts --tenant=<UUID>
  pnpm exec tsx --tsconfig tsconfig.base.json scripts/maintenance/register-lms-templates.ts --tenant=<UUID> --apply

Первый вызов только показывает план. Второй добавляет недостающие версии с approved=false, сверяет байты/контракты и не меняет старые формы, номера или профиль центра. Повтор идемпотентен. Затем директор один раз открывает «Настройки → Формы», просматривает и подтверждает три новые формы. Это отдельная первичная настройка центра, не повторный ввод в операторской подготовке документов. Для нового центра формы устанавливаются штатной регистрацией и также требуют подтверждения. Команда не подтверждает нормативный профиль и не заменяет подпись документа. Для этого запуска фактический старый синтетический центр и сохранность его 19 прежних форм документируются в agent-c/template-upgrade-before.json и доказательствах регистрации/HTTP/UI.
Перед pnpm typecheck или pnpm build на Windows корректно остановить только собственные API и workers, использующие сгенерированный Prisma Client. Иначе DLL может быть занята. Не останавливать соседние процессы. Для сборки также остановить собственный web-процесс, использующий тот же dist-каталог.
  pnpm build

Четыре процесса запускаются в отдельных подготовленных консолях из корня продукта:

  pnpm --filter @demo/web exec next start --hostname 127.0.0.1 --port 3159
  pnpm --filter @demo/render-worker start
  pnpm --filter @demo/integration-worker start

Открыть http://127.0.0.1:3159/login. Синтетические роли и локальная тестовая настройка перечислены в scripts/verification/lms-full-e2e-env.ps1; тестовые учётные записи готовит scripts/verification/lms-full-e2e-fixture.ts. Пароли в этот отчёт не копируются. Для обычной работы используются существующие роли менеджера и директора, для обучения — отдельный LEARNER. Работодатель видит только доступные ему данные по membership.

API слушает 127.0.0.1:4159. Интеграционный worker автоматически завершает истёкшие попытки, готовит внутренний санитарный журнал/список и продвигает согласованные документы. Он не выполняет сетевую передачу провайдеру. Внешнее соединение остаётся NOT_CONNECTED.

Полный discovery и фактическое исполнение новых интеграционных файлов: agent-c/INTEGRATION_DISCOVERY_INVENTORY.json.

Для нового полного браузерного запуска нужен свежий уникальный RunId:

  pnpm exec tsx --tsconfig tsconfig.base.json scripts/verification/lms-full-e2e-fixture.ts
  pnpm test:e2e

Для полного браузерного набора должны работать свежие API, production web и render-worker на указанных loopback-портах. Отдельный постоянный integration-worker на время этого набора не запускать: lms-first-flow-live.spec.ts сам создаёт настоящий дочерний процесс штатного integration-worker, останавливает и перезапускает только принадлежащий ему PID, затем завершает его. Это позволяет проверить восстановление без вмешательства другого worker. После набора для обычной локальной работы снова запустить integration-worker приведённой выше командой. Helper включает текущие producers/consumers старых сценариев DEMO и привязывает checkpoints к этому RunId; не подставлять исторические заявки/evidence вместо нового выполнения. Не менять выключенные/неподключённые реальные провайдеры ради теста. Браузер использует установленный Chrome. Raw trace, cookies, fixture credentials и runtime-логи не публикуются.

Нагрузочную проверку 100 учащихся выполнять отдельно от тяжёлого LibreOffice-рендера и сборки: tests/integration/lms-http.test.ts. Это read/autosave-нагрузка на локальный синтетический стенд, без видео/рендера и без заявления production-capacity. Актуальный результат и точная команда находятся в COMMANDS.json и agent-c/load-1792017682452.json.

4. ДОКАЗАТЕЛЬСТВА И ГРАНИЦЫ

RUN_MANIFEST.json связывает проверенные источники с коммитом реализации. ACCEPTANCE_RESULTS.json содержит ровно 44 критерия и обязательные подслучаи. MVP_COVERAGE_FINAL.tsv сохраняет все исходные 52 строки, включая начальные статусы, и добавляет фактические результаты. UX_ACTIONS.json разделяет первичный ввод, подготовленную задачу, ошибку/восстановление и действия разных ролей. Исходный браузерный замер исключён прямым указанием пользователя «Продолжить без исходного браузерного замера»; экономия времени относительно него не заявляется.

Проверенные документы перечислены точно в agent-a/ROOT_DOCUMENT_PUBLICATION_MANIFEST.json и agent-a/CUREATED_EVIDENCE_REVIEW.json: синтетические DOCX, PDF и изображения фактических страниц. ROOT_DOCUMENT_VISUAL_REVIEW.json содержит SHA просмотренных страниц. Правовой смысл четырёх форм и проверенные выходы приложения сверены в agent-b/LEGAL_FORM_MATRIX_FINAL.json. Результаты приложения и физическая печать — разные факты: физическая печать не выполнялась. Реальное юридическое завершение документа требует применимого профиля, полномочий и обязательных подписей; локальная инженерная проверка это не заменяет.

Провайдер, sandbox, production и отметка ЛМК учитываются независимо в EXTERNAL_GATES.json. Недостающие входы P01–P13 и порядок отдельного подключения — PROVIDER_CONNECTION_PACKET_RU.txt. Карта всех копий ПДн, обязанности и допуски размещения — PERSONAL_DATA_DEPLOYMENT_GATES_RU.txt. Никакая локальная квитанция тестового адаптера, HTTP200/202, выгрузка или ручное подтверждение не являются подтверждением внешнего принятия или ЛМК.
