# Доработка DEMO: оператор вводит людей и исключения, система готовит документы

## Задача и последнее решение пользователя

Доведи существующий DEMO до простого обычного сценария: оператор выбирает организацию или физлицо, вводит/выбирает людей и курсы, проверяет готовый результат, передаёт директору. Стандартные поля документов, часы, формулировки, связанные формы и рассчитываемые даты заполняются системой. Их заполнение не должно требовать отдельного обязательного похода в «дополнительные настройки» каждого обучения или документа.

**Последнее уточнение пользователя: «минимально действий за максимальный эффект».** Требование «один экран» было условным примером, а не обязательной архитектурой интерфейса. Главный критерий — минимум ручного ввода, повторных решений и служебных действий для получения готового результата. Выбирай расположение таблицы, панели, предпросмотра и переходов по тому, насколько они сокращают работу человека. Не пытайся уместить все поля в один перегруженный экран и не создавай отдельный экран/окно для каждого простого действия.

Примеры пользователя — вручную ввести примерно 20 человек или загрузить около 400 из Excel, затем несколькими общими действиями подготовить данные; директору достаточно короткого просмотра и решения, условно 2–3 действий. Эти числа не задают предел людей, число этапов, обязательные шаги мастера или жёсткое число кликов для любого исключительного случая.

Пользователь прямо подтвердил новое правило: **для новой обычной заявки положительный результат по умолчанию; «Ожидает сдачи», «Не сдал», «Не явился» — явно выбранные исключения**. Его формулировка: «если получает, то сдал». Это решение заменяет прежнее требование создавать все новые назначения с UNKNOWN и отдельно подтверждать обычную сдачу. Не возвращай старую политику со ссылкой на предыдущий handoff.

Последний запрос пользователя — понять все пробелы автозаполнения и подготовить этот промпт. Не путай подготовленный промпт с выполненной полной доработкой. После принятия этого промпта к реализации выполни работу целиком, сохраняя уже сделанное, без деления результата на обещанные будущие очереди.

## Что действительно установлено

1. Первый скриншот: у работника для БиОТ отсутствуют минимальные часы теории; БиОТ/ПТМ/ПБ имеют UNKNOWN. Ошибки продублированы по карточкам и протоколам. Положительный исход ранее не подставлялся намеренно: `newAssignment()` давал пустой result, новые комплекты принудительно ставили UNKNOWN/source пустой. Это конфликт прежнего сценария с теперь явно подтверждённым требованием пользователя.
2. Отдельная настоящая ошибка наследования часов: пустое общее поле `hours: ""`/`productionHours: ""` без осознанного CLEARED могло затирать корректные автоматические часы назначения. Локальная проверка воспроизвела рабочие 10/16 и ИТР 40, превращавшиеся в пустые значения при resolve.
3. Второй скриншот содержит пустые ФИО, должность, место работы, БИН/адрес работодателя, отрасль ИТР, результат проверки знаний/прокторинга и профессию/квалификацию ПС. Это не одна проблема «не проставили Сдал». Для неизвестного человека ФИО/должность действительно нужны; известные реквизиты и настройки курса не должны запрашиваться повторно.
4. Дата документа уже задаётся `today(context.tenant.timezone)` при создании. В LIVE_V1 дата протокола наследуется от даты документа; срок действия рассчитывается; ПС имеет UNLIMITED. Период обучения рассчитывается существующим движком только при наличии графика. Нельзя объявлять эти механизмы отсутствующими: нужно проверить их применение во всех входных сценариях.
5. Реквизиты работодателя уже наследуются через `effectiveRecipientEmployer` и серверное разрешение выбранной организации. Для ПС есть fallback из общей профессии/должности строки. На втором скриншоте общая должность тоже пуста. Не добавляй параллельную систему реквизитов или второй справочник профессий.
6. Сейчас `submitProposal(SAVE)` создаёт DRAFT, а `submitApproval()` проверяет полноту перед PENDING. Директор повторно проверяет данные при APPROVE. Поэтому причина появления именно показанной неполной PENDING-редакции в актуальной очереди ещё требует трассировки: старая редакция/старый frontend, другой путь создания, несогласованная версия runtime или ошибка. Не заявляй без доказательств, что нынешнее автосохранение отправляет каждую пустую строку директору.
7. Числовые пути `items.0.assignments.0` отображались как «Сотрудники · 0 · Документы · 0». Это дефект представления ошибок, а не полезная инструкция оператору.
8. У физлица общее место работы находится в «Получатели → Ещё → Указать место работы». В `shared-employer-dialog.tsx` режим заполнения только пустого работодателя пропускает человека, если уже заполнено хотя бы одно поле работодателя. Поэтому одно введённое название мешает дополнить пустые БИН/адрес через этот режим. Нужен режим безопасного дополнения недостающих реквизитов выбранного работодателя без стирания исключений и без скрытого смешивания разных компаний.
9. Отрасль и результаты проверки знаний/прокторинга ИТР находятся в деталях документа; часть обязательного ввода обнаруживается глубоко в разделе «Обучение». Исключения профессии/квалификации ПС тоже раскрываются там, хотя общий fallback уже есть. Упростить нужно доступ к реально недостающим данным, а не просто перенести ещё больше полей в дополнительную панель.

Оно перекрывает ручной/imported/cleared срок и отдельные сроки `biot.ts` для конкретных категорий (например, INSPECTOR_SPECIAL +1 год, COUNCIL без фиксированного срока). ## Целевой обычный сценарий

### Минимум действий для максимального результата

1. **Ручной ввод.** Компактный список, быстрый переход клавиатурой, вставка диапазона из Excel/буфера, добавление следующих строк без открытия отдельной карточки на каждого человека. Общие компания, курсы, даты и профессия для однотипной группы задаются один раз. Если у людей разные должности или условия, их можно изменить по строкам или выбранным группам. Нужные введённые данные, выделение, позиция и черновик не теряются при проверке/возврате.
2. **Excel.** После выбора файла система распознаёт известные столбцы и использует ранее сохранённое подходящее сопоставление. Оператор разбирает только неоднозначные столбцы и проблемные строки в понятном предпросмотре; стандартный знакомый файл не требует заново проходить технический мастер. Импорт не заставляет отдельно открывать каждого человека, не обрезает строки и не сбрасывает уже введённые данные. Сохранить существующие согласование импорта, сопоставление и защиту от дублей.
3. **Общие действия.** Выбрать всех или нужную группу и одним применением назначить курсы/комплекты, работодателя, общую профессию, дату или исключение. Подставить доступные значения, связанные формы и результаты сразу. Не размножать одинаковые операции по числу людей и документов. Показывать понятный охват действия и сохранять осознанные индивидуальные исключения.
4. **Мало решений.** Обычный путь предлагает подходящие значения автоматически и одну очевидную следующую команду. Не заставлять оператора разбираться в служебных идентификаторах, форме каждой пары документов, уровнях наследования, технических партиях и происхождении полей. Настройки центра/программы задаются один раз и используются дальше. Редкие исключения доступны по необходимости.
5. **Проверка и передача.** Проверка и автосохранение происходят в существующем рабочем процессе. «Передать директору» сама сохраняет актуальный ввод и выполняет нужную проверку; не требует предварительно нажать отдельные «Сохранить», «Проверить», «Обновить», «Подготовить» и потом повторить передачу. При ошибке пользователь получает конкретное место исправления, при успехе — ясный статус. Явное согласие на передачу остаётся, дублирующие подтверждения убрать.
6. **Работа директора.** Открыть подготовленную заявку/согласуемую группу, увидеть компактную сводку людей, курсов, дат, исключений и доступный предпросмотр результата, затем согласовать или вернуть с понятной причиной. Не просматривать технический diff как основной документ, не подтверждать отдельно каждого человека и каждую форму, не возвращаться в настройки для обычного решения. Подробности доступны, когда они нужны для осмысленного просмотра; статус, готовые документы и следующее действие появляются без обязательного ручного обновления.

Снижай именно усилия человека. Один клик, запускающий скрытую цепочку обязательных окон и повторных подтверждений, не считается упрощением. Многостраничный интерфейс допустим, если он помогает сделать работу быстрее и понятнее; число страниц само по себе не является метрикой приёмки. Обычные массовые операции не должны становиться длиннее из-за роста числа людей. Ввод уникальных сведений и обработка реальных исключений оцениваются отдельно.

Оператору видны компания/физлицо, компактный список людей, должности/профессии, курсы, дата заявки и понятная готовность. Автоматически подставленные значения доступны для проверки рядом с соответствующим курсом; редкие исключения можно раскрыть. Не заставляй открывать несколько модальных окон, подтверждать одно и то же событие дважды или отдельно вводить исход для карточки, свидетельства и протокола.

Выбор курса должен сразу создавать корректный полный комплект форм. «Готово к согласованию» означает, что обязательные данные действительно разрешены из сохранённых источников. Директор принимает подготовленную редакцию; его кнопка не должна служить первым способом узнать о десятках пустых обязательных полей.

Не выдумывай сведения о неизвестном человеке, организации, числовом балле, внешнем сертификате или фактически проведённой пересдаче. Где существует сохранённый источник — используй его. Где нужна настройка центра — настройка делается один раз на подходящем уровне, а не оператором для каждой формы.

## Исправить сообщения и границу согласования

1. Проверка должна использовать те же разрешённые значения, что сохраняются/фиксируются для печати. Заполненное по наследованию поле не должно одновременно отображаться заполненным и считаться пустым сервером.
2. Общую проблему курса/компании/профиля показать один раз в её контексте. Ошибка конкретного человека содержит ФИО, курс, понятное имя поля и прямой переход к нему. Удалить `professionRu`, `psQualificationRu`, нулевые индексы и внутренние пути из пользовательского текста.
3. Повтор карточка+протокол по одному исходному полю не должен создавать несколько ручных задач. Не объединять одинаковый текст ошибок разных людей так, чтобы часть проблем исчезла.
4. Save/autosave сохраняет незавершённый DRAFT. Передача директору — отдельное явное действие по готовому выбранному составу. Неполная строка/курс не становится PENDING; готовые остальные назначения можно согласовать без ограничения числа партий.
5. Проследить конкретный путь показанных неполных PENDING. Для старых редакций не переписывать payload/hash задним числом и не подставлять вымышленные личные сведения. Предложить понятное возвращение к актуальной рабочей версии и повторную передачу. Новая версия/новые defaults не дают права менять исторический выпуск.
6. Положительный исход, автосохранение, решение директора и выпуск — разные состояния. Автозаполнение не должно автоматически согласовывать или выпускать документы.

## Выполнение и доказательство результата без бесконечных повторов

Сначала составь короткую матрицу всех обязательных полей активных форм с фактическими источниками. Затем исправь связанный сценарий в реальном продукте. Не расширяй дизайн ради нового дизайна и не переписывай уже работающие модули.

Один свежий локальный runtime должен пройти обычное создание, автосохранение, reload, передачу директору, согласование и выпуск/просмотр PDF/DOCX. Не подставляй заранее через API именно те поля, автозаполнение которых проверяешь. Для обычного создания используй настоящий UI. Прочитай сохранённые данные и snapshot; сравни их с текстом и датами реальных печатных документов.

Минимальные содержательные проверки:

- физлицо и организация; новый и сохранённый человек; рабочий и ИТР; все активные направления и формы;
- стандартная выдача без открытия обязательной дополнительной формы результата/графика на каждого человека;
- явные ожидание/несдача/неявка, ручной результат и дата, импортированное и очищенное значение, иной работодатель;
- смена курса/категории/организации/опорной даты, сохранение и повторное открытие; связанные формы остаются согласованными;
- новая строка с одними defaults остаётся технически пустой; частично введённая сохраняется и показывает одну понятную причину неготовности;
- произвольное число людей, курсов и последовательных партий; тестовые масштабы не становятся бизнес-ограничениями;
- старые PENDING, согласованные редакции, выпущенные файлы и их хеши не переписаны автозаполнением;
- новая пересдача не наследует старые оценки другой попытки в KZ/EN; выбранное правило срока одинаково работает в UI, API и документах, включая особые категории ИТР;
- отсутствие лишнего обязательного ввода в обычном пути фиксируется фактическими действиями оператора, а не только PASS unit-тестов.

Отдельно пройди два пользовательских сценария: ручной список примерно на 20 человек и реальный Excel примерно на 400 человек, затем просмотр и решение директора. Это репрезентативные размеры, не пределы. Для каждого запиши краткую последовательность видимых действий до/после: ввод уникальных данных, число повторных общих вводов, подтверждений, вынужденных переходов и исправлений. Отметь, какие действия исчезли и какие остались по объективной причине. Не подменяй 400 строк несколькими вручную подготовленными заявками или циклом API, скрывающим работу оператора. Браузерная автоматизация должна повторять доступный человеку путь. Если больших списков касаются ограничения, покажи их корректную автоматическую обработку и сохранность всего состава. Произвольный лимит «не более трёх кликов» для всех случаев не вводить.

Доработка не принята, если defaults технически появились, но оператор по-прежнему открывает карточки по одной, вводит одно общее значение повторно, делит Excel вручную или проходит обязательные служебные шаги для каждого комплекта; либо если директор вынужден отдельно подтверждать каждую форму. Проверка удобства должна подтвердить сокращение таких действий, а не только правильность результата в базе.

Запусти необходимые lint/type/build и тесты изменённых границ. После успешной проверки повторять прогон только при новой правке или конкретном риске. Пользователь уже просил не тратить время на бесконечное повторение больших наборов.

При реализации до публикации действуют ранее поставленные пользователем требования: сохранить изменения, запушить эту ветку, опубликовать и проверить последний deployment именно её актуального кода, передать рабочую ссылку и действующие роли/реквизиты. Не считать один push доказательством cloud release: здесь frontend Vercel и backend Railway развёртываются отдельно. Не создавать новый сайт/проект. Пароли брать из существующего приватного источника, не менять и не хранить в Git/отчёте. В текущем запросе этот файл является handoff; его создание само по себе не публикует изменения.

## Критерий завершения

Оператор вводит данные человека/выбирает существующие, организацию и нужные курсы, при необходимости меняет исключения. Всё, что определяется этими выборами и настройками центра, уже заполнено, сохраняется и одинаково отражается в UI, проверке, согласовании и печати. Директор получает готовую редакцию. Отчёт показывает оставшийся обязательный ввод с причиной, выполненные проверки, фактические commit/deployment и честные ограничения; не подменяет этим незавершённую работу.

Главный результат — максимально полезное общее действие при минимуме ввода и решений оператора, плюс короткий осмысленный просмотр и решение директора. Конкретная компоновка и число экранов служат этой цели; отдельного обязательного критерия «всё строго на одном экране» нет.
