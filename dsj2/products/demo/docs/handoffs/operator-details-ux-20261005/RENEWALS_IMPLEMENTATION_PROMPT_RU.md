## Реализуй

1. Один раздел с переключателем «По людям» / «По компаниям». Серверный поиск, ответственный, компания, курс, состояние, качество основания; «Сегодня», «Просрочено», 30/60/90 дней. Основная дата фильтра — контакт; альтернативное основание явно подписано. Полные total/counts и cursor, отдельная пагинация дочерних строк/контактов. Не ограничивать видимость первыми 300, не считать totals из страницы.
2. Человек/компания/курс/исходные документы и три разные даты: documentValidUntil, nextCheckDate, contactAfter. Источник, версия политики, проверивший, дата проверки и reason при неизвестности доступны без догадок. VERIFIED_UNLIMITED отдели от DATE_UNKNOWN. ПС не получает фиктивный срок.
3. Единая версионируемая политика с contactLeadDays=30 и attentionHorizonDays=60 как разными настройками. Контакт — от ближайшего подтверждённого применимого основания. Ручная дата/перенос имеет приоритет; изменение расчёта показывает предложение и причину. Календарь Tenant.timezone; документы и аудит неизменяемы.
4. Каноническая потребность на подтверждённого человека + курс/специализацию + цикл обучения. Все формы одного курса — ссылки на доказательства одной потребности. Отличающиеся курсы/категории/циклы не объединяются по названию. Не связывать людей по одному ФИО. Новая политика или повтор reconciliation не создаёт дубликаты; контакты и старые sourceKeys сохранены.
5. Own issued history всех действующих партий, включая частичные; отмена/замена/замещение документов; внешние документы только после проверки identity/источника/применимости. Для внешних источников аддитивно расширь обязательную внутреннюю ссылку RenewalNeed, не создавай фиктивные заявки. Смена компании сохраняет исторического работодателя, требует подтверждения текущей связи и не меняет личность документа.
6. Durable reconciliation внутри автономного DEMO по событиям готовности выпуска/отмены/замены/проверки external/identity/policy и ежедневная ограниченная сверка по timezone. Проверь существующую infrastructure прежде новой очереди; generationJob печати не использовать для скрытых побочных задач. Idempotency, locking, cursor, bounded retry, наблюдаемая ошибка и восстановление обязательны. Это только внутренняя очередь и badge, без email/SMS/WhatsApp/push/сообщений наружу.
7. Контакт, перенос, ответственный, причина, история, новая повторная заявка. Optimistic revision и idempotency контакта; существующий repeated newRequestId preserve. Новое обращение не наследует старые даты/номера/фактические оценки. Групповая повторная заявка компании атомарно связывает выбранные подтверждённые потребности; неоднозначные строки не включаются молча.
8. Раздели качество доказательств и коммерческий статус работы менеджера. Скан не подтверждает покупку/актуальное трудоустройство/законность допуска автоматически. Старые непроверенные сроки и identities видны в «Требует уточнения», а не теряются из счётчиков.

## Проверки и завершение

До миграции сделай synthetic dry-run старых записей: числа дублей, связей, исключений и неоднозначностей; данные не удалять. Проверь upgrade на disposable копии схемы и повторный reconciliation.

Исполни все критерии раздела 7 спецификации. Обязательно 650+ потребностей, несколько форм/курсов/компаний, ПС unlimited, разные три даты, manual перенесённая дата, границы календаря, частичный выпуск, заменённый и внешний документ, повторные/конкурентные операции, tenant isolation и роли.

Из products/demo запусти актуальные обязательные scripts из package.json: lint, typecheck, test, test:integration, test:render, test:e2e, build и git diff --check. Не выключай старые тесты ради зелёного результата. Реальный браузер из свежего build: 1440×900, 1280×720, 768 и узкий экран; поиск → фильтр → контакт → перенос → reload → повторная заявка → возврат к очереди. Зафиксируй source/HEAD/build/PID/cwd/URL, снимки UI и JSON readback, полные counts и отсутствие данных другого tenant.

Веди отдельную acceptance matrix и evidence нового этапа, сохраняя прошлые отчёты и progress. PASS — только исполненный сценарий; невыполненное NOT RUN с причиной. Итог по-русски: что внедрено, как работает менеджер, политика дат и неизвестности, миграционные результаты, дедупликация и исключения, проверки/ссылки/ограничения. Отдельно укажи: локальная готовность, production boundary, внешние рассылки не внедрены.
