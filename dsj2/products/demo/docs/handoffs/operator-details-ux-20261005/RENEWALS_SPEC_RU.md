## 2. Минимальный пользовательский поток

Один существующий раздел «Повторные обращения», переключатель **«По людям» / «По компаниям»**. По умолчанию — мои незавершённые обращения, требующие действия сегодня; счётчик рядом с разделом показывает полное число доступных пользователю обращений. Внутреннее напоминание означает наличие записи в этой очереди, без отправки сообщения кому-либо.

Над списком: поиск по ФИО/компании/номеру документа, ответственный («Мои», выбранный сотрудник, «Без ответственного», «Все»), состояние, курс, компания и фильтры «Сегодня», «Просрочено», «30 дней», «60 дней», «90 дней», «Требует уточнения». Фильтры дат применяются к **следующей дате контакта**. Для срока документа и проверки знаний существует явный дополнительный выбор основания даты; подпись активного фильтра всегда называет выбранную дату.

«По людям»: ФИО, компания, курс, краткое основание и следующая дата контакта; строка раскрывает документы и три отдельные даты. Несколько курсов одного человека — отдельные потребности в одной группе. «По компаниям»: компания, число людей, число активных потребностей, ближайший контакт, ответственный/«несколько»; раскрытие загружает сотрудников постранично, не скачивает весь tenant. Человек без подтверждённой компании остаётся в группе «Компания требует уточнения».

Карточка потребности показывает:

- Подтверждённую identity человека, компанию исторического выпуска и отдельно текущую подтверждённую связь с компанией.
- Курс/категорию/специализацию, исходные документы, номер/дата/эмитент, источник срока и закреплённую версию политики.
- «Документ действует до», «Следующая проверка знаний», «Следующий контакт». Пустое значение выводится объяснимым состоянием, а не прочерком, который можно принять за бессрочность.
- Последний контакт, ответственного, причину переноса/закрытия, полную постраничную историю.
- Действия «Записать контакт», «Перенести», «Уточнить сведения», «Неактуально», «Создать повторную заявку». Сохранение контакта и новая дата выполняются одним действием; перенос требует дату и причину.

Обычная работа: открыть очередь → выбрать строку → записать результат контакта/дату → вернуться к сохранённому фильтру и позиции. Создание повторной заявки использует существующую идемпотентную команду; повтор клика возвращает ту же новую заявку. Для компании можно выбрать несколько подтверждённых потребностей и подготовить одну заявку с сохранением связей каждой потребности; это отдельная атомарная операция, без скрытого объединения людей или обучения.

## 3. Три даты и единая политика

| Дата                 | Источник                                                                                          | Чего она не означает                                               |
| -------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| `documentValidUntil` | Фактический собственный/проверенный внешний документ и применимая подтверждённая версия правила   | Не равна следующей проверке знаний и не доказывает допуск к работе |
| `nextCheckDate`      | Явная дата в проверенном источнике либо расчёт по утверждённой политике с известной базовой датой | Не выводится простым копированием срока документа                  |
| `contactAfter`       | Ручная договорённость менеджера либо автоматическое предложение из даты основания                 | Не изменяет юридические/печатные даты документа                    |

Предложение первой версии `RenewalPolicy`: `contactLeadDays=30`, `attentionHorizonDays=60`, горизонт пользовательских фильтров 30/60/90, календарь — `Tenant.timezone`. Это **два разных параметра одной версии политики**: за 60 дней источник подсвечивается как приближающийся, за 30 дней появляется автоматическая рекомендуемая дата контакта. Они не заменяют друг друга. UI не должен утверждать «нужно связаться сегодня» только по состоянию APPROACHING.

Основание автоматического контакта — ближайшая из подтверждённых применимых `documentValidUntil` и `nextCheckDate`; API возвращает `contactBasis`, исходную дату и версию политики. При равных датах хранится список обоих оснований. Ручной `contactAfter` и перенос имеют приоритет и не перезаписываются пересканом. При изменении фактов UI показывает новое предложение и причину, сохраняя договорённость менеджера до явного изменения. Уже наступившее рекомендуемое число остаётся прошлой датой и попадает в «Просрочено»; его нельзя каждый день передвигать на сегодня.

Время сравнивается как календарная дата `YYYY-MM-DD` по часовому поясу центра, а timestamps аудита — UTC. «Сегодня» включительно; «Просрочено» строго раньше сегодня; «30/60/90 дней» — сегодня…сегодня+N календарных дней включительно. Закрытые и заменённые потребности не входят в рабочие счётчики, но доступны в истории. Разные фильтры могут пересекаться; UI не складывает их счётчики в общий итог.

В текущем LIVE_V1 ПС имеет `validityMode=UNLIMITED`, `validUntil=""` (`businessValidity` в `packages/contracts/src/business-rules.ts`). Это продуктовая политика, **не юридическое заключение**. Для ПС показывать «Бессрочно по подтверждённой политике», если источник и применимость подтверждены. Не придумывать срок ради напоминания; отдельная проверка знаний/контакт возможны только при собственном подтверждённом основании. Пустая дата в старом или внешнем документе сама по себе не означает бессрочность.

## 4. Достоверность и дедупликация

Две независимые оси состояния:

1. Качество основания: `VERIFIED_FIXED`, `VERIFIED_UNLIMITED`, `DATE_UNKNOWN`, `SOURCE_UNVERIFIED`, `IDENTITY_UNCONFIRMED`, `POLICY_UNCONFIRMED`, `SUPERSEDED`, `CANCELLED`. Надписи человекочитаемые; детальные reason codes доступны при раскрытии.
2. Работа менеджера: существующие `NEEDS_REVIEW`, `CONFIRMED`, `CONTACTED`, `DEFERRED`, `IRRELEVANT`, `ORDER_AGREED`. Не превращать проверенный документ автоматически в подтверждённую потребность в новой покупке.

Одна активная потребность соответствует человеку + направлению/специализации + фактическому циклу обучения в tenant. Канонический `trainingIdentity` выводится из immutable issuance/event/получателя, с различением категории, программы/специализации и реального повторного обучения. Все удостоверения, свидетельства и протоколы одного цикла связаны как доказательства этой потребности. **assignmentId отдельной печатной формы больше не является ключом независимой потребности.** Общее название курса без подтверждённого идентификатора недостаточно для автоматического объединения.

При новом подтверждённом цикле предыдущая активная потребность закрывается/замещается со связью `supersededBy`; её контакты остаются. Повтор скана, конкурентные процессы, изменение версии политики или появление второй формы того же цикла обновляют производную часть существующей записи. История контактов и ручные решения не удаляются. Неоднозначные старые строки не объединяются по совпадению ФИО: они остаются в «Требует уточнения» до существующей сверки получателей.

Компания не входит в ключ личности/курса. Смена работодателя меняет подтверждённую текущую группировку и routing ответственного, но сохраняет компанию исходного документа и историю. `RecipientEmployment.period` сейчас свободный текст, не надёжная текущая временная связь. До явного подтверждения показывать обе версии и «Текущая компания требует уточнения», не угадывать по последней строке.

Отмена/замена: сверять `IssuanceEvent` CANCELLED/REPLACED/SUPERSEDED и `IssuedDocument.replacesDocumentId`, а не только статус заявки. Не вычислять срок по отменённому источнику. Если другая действующая форма подтверждает тот же цикл, она остаётся основанием; иначе потребность переводится на уточнение, с сохранением прошлых дат как истории. Отменённая повторная заявка не должна навсегда скрывать потребность; возвращение в очередь — с видимой причиной и без создания дубликата.

Внешние документы: использовать `ExternalEvidence` и его проверку, tenant-scoped identity/компанию. Нужна явная связь с serviceKey/категорией/версией политики; текстовое похожее название не даёт автоматического срока. Внешняя запись UNVERIFIED не создаёт уверенное истечение. Существующая обязательная ссылка RenewalNeed на внутреннюю заявку требует аддитивного расширения источника; не создавать фиктивную внутреннюю заявку для внешнего документа.

## 5. Обновление внутри автономного DEMO

Будущая реализация включает server-owned reconciliation после готовности выпуска, отмены/замены документа, проверки внешнего документа, подтверждения identity/работодателя и активации проверенной политики. Использовать immutable issuances всех действующих партий, в том числе частичных, а не только последнюю issuance FINALIZED-заявки. Простая регистрация новой черновой заявки не создаёт подтверждённый документ.

Команда `reconcileRenewals(tenant, sourceRefs)` идемпотентна и транзакционна для производной потребности. Для доставки событий нужен небольшой durable task/outbox автономного DEMO с уникальным ключом источника, cursor, ограниченным batch, retry и журналом ошибки. Не подмешивать reconciliation в `generationJob` печати и не запускать DSJ notifications. Если существующая инфраструктура допускает durable DEMO task без отдельной таблицы, использовать её после проверки, а не создавать вторую очередь автоматически.

Один ежедневный reconciliation по календарю центра компенсирует пропущенные события и обновляет временные индикаторы. Переход календарного дня не изменяет источник/ручные даты. На первом этапе доставка — только вычисляемый badge и очередь внутри программы. Нет email, SMS, WhatsApp, browser push, сообщения менеджеру наружу или отправки клиенту. Внешняя доставка — самостоятельный будущий проект с отдельным разрешением.

Начальная сверка существующих данных — dry-run с числами «связано/объединено/требует уточнения/исключено», затем применение новой миграции только на согласованном окружении. Исторические строки/контакты не удалять; сохранять старый sourceKey и соответствие canonical need. Повтор миграционной сверки должен быть безопасным.

## 6. Минимальные дополнения контрактов и данных

- `GET /renewals`: query `view=people|companies`, search, ownerId, customerId, serviceKey, state, quality, dateBasis, dateWindow, cursor, pageSize (например 50, максимум 100). Ответ `{items,total,counts,nextCursor,asOf,timezone}`. Счётчики считаются по всей подходящей выборке в БД; group totals отдельно от number of needs. Порядок детерминированный по contactAfter/null-last и id. Нельзя получить total из `items.length` или старых 300 строк.
- Отдельная пагинация людей компании и контактов потребности; групповые итоги не требуют загрузки всех дочерних строк. Индексы tenant+owner/state/contactAfter и tenant+customer/serviceKey; проверить планы запросов на больших данных.
- `RenewalNeed`: канонический course/cycle key, `serviceKey`, server-owned список ссылок на доказательства, качество основания, связь замещения, версия расчёта и происхождение `contactAfter`, revision для конфликтов. Старые sourceRequestId/sourceRowId/assignmentId сохранить для совместимости; аддитивно разрешить внешний source с проверяемым discriminator. Полная схема проверяет: есть хотя бы один валидный источник, внутренние поля только вместе, tenant берётся из сессии.
- Версионируемая политика хранит два горизонта, тип основания следующей проверки, источники/проверившего/дату, применимость и timezone basis. Сервер выдаёт расчёт с происхождением; браузер не присылает вычисленные даты как подтверждённые факты.
- PATCH/contacts принимают expectedRevision; новая запись контакта принимает idempotencyKey. История контакта append-only; исправление — новая заметка со ссылкой. Уже действующий retry создания повторной заявки сохранить.
- Статус current employer подтверждается через существующий RecipientEmployment с минимальной явной metadata актуальности; не превращать строковый `period` в достоверные даты без сверки.
- Список собственных/внешних доказательств ссылается на существующие документы; отдельного параллельного реестра корочек не вводить.

Это проект контракта, не уже доступные поля/API. Подробную миграцию определить после проверки актуальной схемы следующего этапа; применённые миграции не переписывать.

## 7. Приёмка будущей реализации

1. Более 300 (минимум 650) потребностей: серверные фильтры, обе группировки, total/counts и cursor охватывают каждую запись без дублей/пропусков. Смена фильтра сбрасывает cursor; concurrent insert не теряет/не повторяет уже показанные страницы.
2. Один человек с тремя печатными формами одного обучения — одна потребность и три доказательства; другой курс/категория/специализация/новый цикл остаётся отдельным. Неподтверждённые совпадения ФИО не сливаются.
3. Документ до D, проверка D+20, контакт D−30 показываются отдельно. APPROACHING с D−60 не меняет дату контакта. Ручной перенос переживает любой перескан. ПС unlimited не получает фиктивную дату.
4. Проверка границ сегодня/вчера/30/60/90, високосного года и перехода суток в timezone центра. Изменение часового пояса явно отражено в расчёте и не переписывает договорённости.
5. Новый/частичный выпуск, отмена/замена, внешний UNVERIFIED→VERIFIED→SUPERSEDED, смена компании и подтверждение личности обновляют очередь. Повтор/конкуренция/retry worker не создают дубликаты; сбой показывает управляемое состояние и возобновляет cursor.
6. Записать контакт → reload → перенос → история → подтверждение → повторная заявка. Двойное действие не создаёт два контакта/две заявки. Старые результаты, даты и номера не попадают в новый выпуск автоматически.
