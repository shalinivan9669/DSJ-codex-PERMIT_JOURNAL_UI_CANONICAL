## 1. Что пользователь считает главным

Это программа для оператора. Главный критерий — понятная непрерывная работа: оператор видит, что заполнить, сразу исправляет ошибку и получает документы без поиска действий по разным экранам. Технические возможности и масштабирование не компенсируют неудобство формы; их пользовательская ценность должна быть видна в обычной работе, а не только в отчёте о тестах.

Дословные опорные требования из разговора:

- «У прежней формы сильнее ощущение понятной, непрерывной работы» — пользователь выделил это как основную мысль.
- «это программа для оператора».
- «простое необходимое», «пространство без лишнего».
- `/requests/new` — только физлицо / организация и «Далее». Не переносить сюда редактор.
- «в одну строку делаем и все там удобно для оператора» — крупные отдельные панели получателей были явно отвергнуты.
- Текущий визуальный стиль можно оставить; нужно исправить поведение и качество расположения полей.
- Новое замечание: можно назначить обучение всем, но нельзя снять его там же; поля заполнения расположены на разных уровнях.

Нужен компактный строковый ввод с приятными полями и ясными действиями. Не превращать его ни в тяжёлую электронную таблицу, ни в многошаговый мастер, ни в стопку карточек на каждого человека.

## 4. Два подтверждённых дефекта

### A. Одностороннее назначение обучения

Источник: `apps/web/components/request-training-choices.tsx`.

- При наличии отмеченных строк целевая группа — они; без отметок — все `draft.items`.
- `assigned` вычисляется по направлениям через `trainingDirection`.
- При `assigned === recipients.length` ставится `complete`.
- `disabled={disabled || !recipients.length || complete}` отключает кнопку, а обработчик дополнительно выходит при `complete`.
- Единственный путь действия вызывает `assignTrainingBundle`; обратного действия у этой панели нет.

Внешне чип с галочкой напоминает переключатель, но фактически является кнопкой «добавить один раз». Это противоречит ожиданию пользователя. Удалить только `complete` из `disabled` недостаточно: получится повторное добавление без снятия и без контракта сохранности данных.

`apps/web/lib/request-bundles.ts` связывает назначения с событиями обучения (`events`), комплектами обязательных документов, категориями и режимом протокола. `recipientForRequest` наследует однозначные события при добавлении новых людей. Поэтому простое удаление assignments с оставленным активным event может вернуть снятое направление следующей строке. Это ограничение для оценки вариантов, а не поручение сейчас реализовывать удаление.

Дополнительные факты code review: существующий undo массовых операций в `editor.tsx` не используется этими чипами — они вызывают обычный `edit`. В `recipient-details.tsx` обычное удаление скрыто при `liveRules`; переключение в детали не следует считать доказанным обходным путём. Восстановление удалённого результата через обычный PATCH может заново установить `confirmedBy/confirmedAt` (`apps/api/src/requests.ts`): нельзя обещать сохранность происхождения результата, не проверив серверное поведение. В анализе отдельно различать простое снятие ошибочно выбранного пустого комплекта и снятие обучения с уже введёнными фактами.

### B. «Пляшущие» поля

Источники: `apps/web/components/recipient-grid-row.tsx`, `recipient-grid.css`, `operator-form.css`.

Базовое `vertical-align: middle` центрирует **всё содержимое ячейки**. В ячейках ФИО и RU после input могут появляться `small.field-hint`, `field-error`, `TextQualityHint`; в KZ, фото и действиях такого содержимого может не быть. Центры самих input перестают совпадать. Убрать проблему только одинаковым `min-height` input нельзя.

На приложенном снимке ФИО и RU расположены выше KZ/фото/действий. Это визуально подтверждено снимком, условная структура и CSS подтверждены чтением кода. Изменение координат во время ввода в этой подготовке не измерялось; будущая проверка должна воспроизвести его до правки.

Требуется контракт основной линии контролов и отдельной зоны обратной связи. Не скрывать ошибки, не обрезать их `overflow:hidden`, не назначать всей строке жёсткую высоту и не компенсировать отдельные поля случайными `margin-top`.
