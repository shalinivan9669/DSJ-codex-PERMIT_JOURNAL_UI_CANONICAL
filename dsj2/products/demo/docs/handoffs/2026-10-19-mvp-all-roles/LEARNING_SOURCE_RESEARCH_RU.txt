3. КОНКРЕТНЫЕ НЕЗАКРЫТЫЕ МЕСТА/РИСКИ ПО ИСХОДНИКАМ
L1. Смена собственного пароля не доведена до кабинетов новых ролей. Форма PasswordForm и вызов /auth/password находятся только в components/settings.tsx:971+, API маршрут разрешён всем известным ролям. Однако components/workspace.tsx направляет LEARNER и все teachingRole в LmsWorkspace независимо от /settings, EMPLOYER — в EmployerHome; в LmsWorkspace для /settings нет ветки. LmsProfile не содержит смены пароля; /security управляет MFA и резервными кодами, а не паролем. Следующий чат должен дать каждой роли рабочий путь смены своего пароля и проверить повторный вход/инвалидацию старой сессии. Не подменять эту проверку администраторским сбросом.
L2. Саморегистрация слушателя имеет локальную конфигурационную зависимость: identity.ts:79+ требует DEMO_LMS_REGISTRATION_TENANT_ID и active tenant, иначе REGISTRATION_CLOSED. Значение текущего окружения здесь не читалось. На входе ссылка «Зарегистрироваться на обучение» выводится всегда. Проверить фактический локальный маршрут регистрации в правильный центр; закрытая регистрация должна быть понятным состоянием с реальным приглашением, не кнопкой в тупик. Не записывать секреты в handoff.
L3. Автор может выбрать requiresProctoring в course-editor.tsx:1003; final-admission.ts:55+ безусловно блокирует финал при этом флаге, result-finalization.ts требует !requiresProctoring. Это подтверждённый source-level тупик локального экзамена для такой конфигурации. Не имитировать прокторинг и не отключать требование тихо. Определить разрешённый MVP маршрут: честно недоступная конфигурация с понятной ответственностью до назначения либо реальный доказуемый процесс, если он нужен MVP. Внешний провайдер не появляется от локальной реализации.
L4. practiceEvidenceMode=IN_PERSON доступен в редакторе, но practice-requirement.ts:34+ возвращает satisfied:false для IN_PERSON или metadata.format=IN_PERSON. Рабочая реализованная ветка — REVIEWED_ASSIGNMENTS с принятием всех обязательных работ. В пределах нужного MVP исключить ложное обещание, что очная практика уже может быть подтверждена кнопкой; сценарий очной программы отдельно классифицировать по ТЗ и фактическому процессу.

4. ОБЯЗАТЕЛЬНЫЕ СКВОЗНЫЕ ПРИЁМОЧНЫЕ СЦЕНАРИИ ДЛЯ НОВОГО ЧАТА
А. Чистая METHODIST без bindings: входит, видит свой кабинет, создаёт RU/KZ программу, модуль, текст/видео/PDF, вопросы банка и промежуточный/итоговый тест; загрузка/автосохранение/перезапуск страницы; отправляет на проверку. ADMIN возвращает с замечанием, методист исправляет, ADMIN публикует. Опубликованная версия неизменна, новая версия не меняет ранее назначенную.
Б. LEARNER самостоятельно регистрируется либо принимает реальное приглашение, входит, видит только своё обучение, проходит все обязательные элементы, возобновляет видео/попытку после перезагрузки, получает осмысленную причину недопуска; сдаёт фактический финал. Успех/ошибка/ручная проверка/исчерпание попыток/истечение доступа — разные состояния.
В. TEACHER работает с назначенной группой: видит прогресс, проверяет открытый ответ/файл, возвращает работу с замечанием, слушатель исправляет, преподаватель принимает. Решение появляется у слушателя и организации. Если занятие используется в MVP программе, реальная отметка посещения влияет только на эту группу и соответствующий элемент.
Г. EXPERT видит только назначенные результаты/протоколы, подтверждает правильную ревизию; отзыв полномочия запрещает действие из уже открытого окна. Право подписанта отдельно. Самопроверка и чужие группы/tenant недоступны даже прямым API и файлами.
Д. LEARNER после результата получает фактически выпущенные протокол/сертификат/удостоверение по программе, скачивает PDF, открывает QR/публичную проверку; отмена/замена видна корректно. Учебный PRACTICE и обычный печатный PASSED/AUTO никогда не считаются VerifiedExamResult для выдачи LMS документов.
Е. Все эти роли проходят свои задачи на RU и KZ, desktop и мобильной ширине; формы не обрезаны, видео играет, PDF доступен, возврат/назад не теряет ввод, 401/403/409/ошибка сети объясняют следующий шаг без технической каши.
Ж. Матрица негативных сценариев: другая организация/группа/tenant/слушатель, отозванный binding, частичный membership, закрытый курс, изменение ID в URL, архивный материал, уже использованный invite/recovery token. Проверять действие и выдачу данных/файлов, а не только отсутствие кнопки.
