5. ОБЩИЕ ИНВАРИАНТЫ

- Единая модель человека и организации. Совпадение имени, телефона, почты или введённого БИН само по себе не даёт права объединить людей, привязать существующий аккаунт, получить employer membership или раскрыть внутреннюю запись.
- Tenant и права берутся из доверенной сессии. Для анонимной заявки tenant определяется только разрешённым серверным контекстом публичного центра/каталога; client tenantId/customerId/role не авторитетны.
- Scope одинаков для list/count/search/detail/action/export/file/background/direct URL. Новые маршруты deny-by-default. Отзыв membership/учебного назначения/роли учитывается без нового логина; заранее подготовленный экспорт не должен обходить отзыв.
- Регистрация, заявка, зачисление, просмотр урока, LEARNING completion, результат экзамена, accepted practice, официальный допуск, approval, подпись и выданный документ — разные факты.
- PRACTICE и обычная печать PASSED/AUTO не создают verified LMS result. Оплата не создаёт результата, допуска или документа. Уведомление/его прочтение не засчитывает учебное действие.
- Сохраняй FINAL/INTERMEDIATE/LEARNING_FINAL, manual review, immutable published snapshots, историю ответов/работ, реальные gates документов и подписантов. Нельзя сделать тест зелёным отключением review/signature/legal checks.
- Старые назначения, dueAt, доступ, происхождение, история заказов, оплаты и подписей не получают выдуманный backfill. Неизвестное остаётся неизвестным.
- Срок доступа к курсу, deadline попытки, дедлайн задания, дата занятия, срок действия документа и дата следующего обучения не взаимозаменяемы. Все календарные правила имеют явно заданную timezone; не выводи её из часового пояса машины.
- Согласие и полномочия фиксируются явно по существующим правилам. Не выдавай synthetic fixture за реальное юридическое основание.
- Изменения данных атомарны или имеют явный durable job/компенсируемый этап; retry не дублирует сущности и номера. Одинаковый idempotency key с другим payload отклоняется.
- Логи и audit полезны для расследования, но не хранят пароли, TOTP seeds, recovery codes, session cookies, сырые файлы, избыточные ИИН или содержимое закрытых ответов. Заголовок X-Forwarded-For доверять только при явной настройке доверенного proxy.

Сделай доступный через UI путь «Подробнее → Записаться → состояние заявки → Начать/Продолжить обучение». Развивай существующие каталог, identity и learner workspace. Известные имя/контакт/организацию не просить вводить заново.

Публичность программы должна быть явно разрешена: публикация учебной версии сама по себе не открывает её в анонимном каталоге. Безопасный default для старых курсов — не менять существующую видимость. Публичная проекция содержит только разрешённые описательные поля и актуальность набора; не отдаёт внутренний DTO, материалы, ответы, draft/review, закрытые цены или данные людей.

B2C может предварительно выбрать курс, затем пройти существующую регистрацию/вход и сохранить выбор. Авторизованный слушатель отправляет заявку, видит свою историю и исправимую причину отказа/возврата, отменяет ещё не обработанную заявку в допустимом состоянии. Подтверждённое назначение открывает существующий учебный путь.

B2B-заявка: организация, БИН, контактное лицо, телефон, e-mail, должность, курс, количество сотрудников, комментарий. Обязательность каждого поля определи обоснованно, не делай B2C фиктивной организацией. Поддержи безопасный анонимный приём на серверно определённый центр без выдачи внутренних списков. Известному работодателю подставь данные подтверждённой организации.

Квитанция подтверждает сохранение заявки, а не её принятие, оплату или зачисление. Название центра берётся из подтверждённой конфигурации; фраза из §44 про ТОО РЦОиПК не должна безусловно подменять другие автономные установки.

Повтор запроса/двойное нажатие/параллельная отправка должны давать идемпотентный результат в определённом контексте, с серверным повторным контролем версии/доступности курса. Не допускай спама через неограниченные payload/частоту/хранилище; анонимная защита работает локально без обязательной внешней CAPTCHA.

ИНЖЕНЕРНОЕ РЕШЕНИЕ ЭТОЙ ВОЛНЫ: если программа не содержит уже существующего явного правила самостоятельного зачисления, B2C-заявка идёт в управляемое принятие центром. Отсутствующая цена не означает бесплатно, отправка формы не означает право немедленно учиться. Онлайн-магазин, платёж и автоматическая доставка приглашений не имитируются.

7. N02 — РАБОЧАЯ ОЧЕРЕДЬ ЦЕНТРА И СВЯЗАННЫЙ ЗАКАЗ

Основание: TZ-43-01, §43 ¶954–968; локальная часть TZ-45-01, §45 ¶994–1012; инвариант TZ-46-02, §46 ¶1028.

Продолжи существующие ServiceOrder, OrderMilestone, PaymentEvent, PrintRequest и связи Enrollment. Не создавай параллельную CRM/финансовый реестр. Отдельная сущность входящей заявки допустима как недостающее звено, но после обработки она должна ссылаться на существующий заказ и назначения.

Сотрудник центра видит очередь заявок: состояние, ответственный, организация/слушатель, программа, количество, дата и следующее действие. Принимает/возвращает с причиной/отклоняет, связывает проверенные существующие данные либо создаёт разрешённые новые без повторного набора известного. Параллельное принятие одной заявки не создаёт двух заказов или назначений. Перед записью повторно проверяются права, версия и доступность программы.

Поддержи понятные бизнес-стадии из §43: новая; в обработке; контакт установлен; КП отправлено; договор; счёт; оплачено; обучение; завершено; документы выданы; закрыта. Это не один произвольно редактируемый enum, который подменяет независимые факты. Определи переходы, основания, actor/time/reason и конфликты; используй факты/этапы существующего заказа.

Для КП, договора и счёта свяжи уже существующие документы/частные вложения/реквизиты и ручные подтверждённые свидетельства. Если тип вложения требует новой поддержки — добавь её в действующий private storage с валидацией. Не сочиняй юридические тексты договоров, реквизиты и реальные шаблоны. Локальная генерация файла не означает «отправлено»; ручная отметка внешнего события явно содержит происхождение, время и автора.

Для оплаты используй действующий механизм ручного PaymentEvent и вычисления сумм/сверки. Не вводи второй независимый paid-флаг и не разрешай считать неизвестную сумму оплаченной. Платёж/возврат в тесте — только синтетический локальный факт, не реальная транзакция.

Учебная часть и документная часть заказа вычисляются из фактических назначений/результатов/выдач с историей; частичный выпуск и отмена/замена видны корректно. Не называй заказ полностью выданным по первому PDF. Для неплатного/неприменимого коммерческого этапа допускай явную причину, не создавай фиктивные договор/счёт/оплату.

Старые OPEN-заказы сохраняют своё значение и неизвестные этапы. Полная автоматизация внешней коммерческой цепочки §45 останется ограниченной, даже если локальный workflow выполнен; это отражается в матрице.

8. N03 — СОТРУДНИКИ РАБОТОДАТЕЛЯ И АВТОМАТИЧЕСКОЕ МАССОВОЕ НАЗНАЧЕНИЕ

Основание: TZ-31-01, §31 ¶718–733; развитие TZ-30-01/02, §30 ¶698–712.

Работодатель с подтверждённым membership работает только со своей организацией. Добавление вручную, загрузка Excel и массовый ввод используют существующие Recipient/Employment и механизмы reconciliation. Поля источника: ФИО, ИИН, телефон, e-mail, должность, курс. Не делай ИИН обязательным техническим ключом для любого сценария, если действующие правила допускают отсутствие; отсутствие идентификатора не разрешает угадывать совпадение.

Сделай загрузку → предпросмотр → сопоставление → исправление только исключений → подтверждение валидного списка. Сохраняй черновик и выбранную программу/версию, группу, общие сроки и происхождение заявки/заказа. Для повторных людей не требуй повторного ввода. Дубли внутри файла и с существующей базой не должны незаметно создавать вторую карточку или второе назначение.

ВАЖНО: §31 ¶733 прямо требует «После загрузки система автоматически назначает обучение». Поэтому после подтверждения корректного списка пользователем с явным действующим правом назначать обучение запускай существующий durable batch автоматически, без отдельного ручного согласования каждой строки центром. Выбор файла сам по себе ещё не является подтверждением всех неоднозначных записей.

Для membership без права назначения допустима отдельная ветка «отправить список центру». Она не заменяет автоматическую ветку и не даёт основания объявить TZ-31-01 выполненным целиком. Не расширяй права всех EMPLOYER глобально: назначение разрешается по действующим/явно предоставленным полномочиям организации и доступности курса. Не изобретай универсальную роль суперработодателя.

Проверка файла ограничивает размер, число строк/листов и вычислительные затраты. Excel не исполняет макросы/внешние ссылки/формулы; недопустимые и потенциально опасные ячейки объясняются по строкам. Имена/тексты не попадают как формулы в экспорт ошибок.

Корректные и ошибочные строки имеют явный результат. Обработка bounded chunk, per-row идемпотентность, сохранённый progress, retry/resume после рестарта/сбоя, предсказуемая отмена только ещё не выполненного. Повторное подтверждение/загрузка не дублирует завершённые строки, если это тот же намеренный batch; новое легитимное повторное обучение оформляется явной новой операцией, а не запрещается навсегда уникальностью person+course.

Превью не резервирует право навсегда: перед выполнением проверяются актуальные membership/курс/версия/группа. Если права отозваны посреди job, остаток не выполняется; уже выполненное не исчезает молча. Покажи итог и путь исправления.

9. N04 — РАБОЧИЕ КАБИНЕТЫ И СЛЕДУЮЩЕЕ ДЕЙСТВИЕ

Основание: развитие TZ-30-02, TZ-17-02, TZ-71-01; §17 ¶426–428, §30 ¶704;711–712, §71 ¶1477–1487. Связь с N01–N03 и N05; полный новый кабинет не требуется.

В существующем кабинете слушателя свяжи заявки, мои курсы/прогресс, ближайшие события, допустимый тест, результат, готовые документы и внутренние уведомления. Показывай следующее реальное действие и понятный статус, включая ожидание принятия, проверки работы, разрешённой подписи или недостающего основания. Если действий нет — понятное пустое состояние и переход в разрешённый каталог.

Профиль и настройки: показывай известные данные, разреши править только реально разрешённые поля и настройки внутренних уведомлений. Смена подтверждённого идентификатора/связи человека требует действующего защищённого workflow; её нельзя сделать обычным patch профиля. Критические уведомления по обязательным действиям не исчезают из-за отключённого декоративного счётчика.

Работодатель видит сотрудников/группы, сроки, прогресс, результаты, доступные массовые операции и только допустимые готовые файлы. Сохрани рабочие фильтры, выбор между страницами и явную область «выбранные / вся отфильтрованная выборка». Смена фильтра не должна незаметно включать посторонних в batch.

Центр работает из общей очереди с переходом в существующие детали, без нескольких дублирующих карточек для одной операции. Статусы заявок/заказов/обучения/документов связаны, но не подменяют друг друга.

Не превращай экран в набор новых плиток, повторяющих списки. Существующие обычные печать и назначения не должны получить дополнительный обязательный визит в CRM, согласование или диалог.

10. N05 — ДОЛГОВЕЧНЫЕ ВНУТРЕННИЕ УВЕДОМЛЕНИЯ И НАПОМИНАНИЯ

Основание: TZ-41-01, §41 ¶908–925; внутренняя часть TZ-41-02, ¶933; TZ-73-02, §73 ¶1531; поддержка TZ-17-02/TZ-71-01.

Расширь существующий LmsLearningNotification/SESSION inbox до общего локального механизма с явно типизированными источниками. Сохрани старые уведомления, историю readAt и scope; не создавай второй несвязанный inbox.

Обязательные события §41: регистрация, зачисление, назначение курса, начало, напоминание, допуск к тесту, результат, выдача документа, истечение срока. Для каждого определены событие-источник, получатели по правам, момент фиксации, язык/шаблон, deep link и ключ дедупликации. Не создавай несколько одинаковых сообщений «зачисление/назначение» от одного факта без пользовательского смысла; сохрани явную семантику типов.

Начало — реальное начало либо подтверждённая запланированная дата, не произвольный login. Допуск к тесту возникает при фактическом переходе eligibility, а не каждом GET. Выдача означает разрешённый issued/document-ready факт существующего workflow, а не создание job.

90/60/30/7 дней реализуй для известных релевантных сроков действия документа/следующего обучения, сохраняя отдельно напоминания доступа/задания/занятия. Не выводи дату действия удостоверения из accessDays. Если дата/нормативное основание неизвестны, показывай unknown/задачу уточнения без выдуманного расписания.

Транзакционная фиксация события либо существующий outbox, идемпотентная доставка во внутренний inbox, bounded worker, claim/lease/retry, уникальный delivery key и сохранённый результат. Не нужен внешний брокер, если задача решается существующими PostgreSQL/worker средствами.

Документируй catch-up после простоя, границу создания исторических уведомлений, изменение даты/отмену/замену источника, timezone и переход суток. При запуске новой системы не отправляй пользователю весь исторический архив. При нескольких пропущенных порогах покажи уместное актуальное напоминание, не лавину устаревших дублей; выбранное правило зафиксируй как ENGINEERING_DECISION.

Прочтение одного/всех, unread count, pagination, reload, безопасный переход к источнику. При отзыве доступа уведомление и его счётчики/текст/ссылка не раскрывают недоступные данные; сервер проверяет актуальные права. У работодателя уведомления только в разрешённой области и без чужих персональных данных.

Работает при закрытом браузере через локальный worker. Toast или вычисляемая карточка срока не заменяют сохранённую доставку. Внешние Email/SMS/WhatsApp/push остаются отключены; статус SENT для них не выставляется, реальных отправок нет.

11. N06 — СВОДКИ, ФИЛЬТРЫ И ЕДИНЫЕ ОПРЕДЕЛЕНИЯ

Основание: TZ-47-01, §47 ¶1034–1045; TZ-47-02, ¶1047–1055; поддержка TZ-37-01 и TZ-30-02.

Сделай компактную рабочую сводку с переходом в составляющие строки: пользователи, организации, активные/завершённые курсы, тесты/пройденные тесты, выданные/действующие/истекающие/аннулированные документы. Никаких красивых, но несверяемых чисел.

До реализации зафиксируй определения: что считается пользователем/участником; программа или назначение в «активных/завершённых»; попытка или человек в «тестах»; период события; handling повторных попыток/переобучения; текущий результат и исторический; document issue vs file. Если нужны оба показателя — назови их явно, не складывай разные единицы.

Статистика учитывает только разрешённые данные до агрегации. Текущий действующий документ определяется существующим workflow, отменой/заменой, известной датой действия и необходимыми подписями. Отсутствие даты действия не означает бессрочность, отсутствие данных не превращается в ноль.

Фильтры §47: дата, курс, организация, БИН, город, преподаватель, статус. Применяй одни нормализованные параметры и predicate к списку, count, summary и отчёту. В нескольких предметных представлениях явно указывай, к какому событию/сущности относится дата и статус. Комбинация фильтров и пустая выборка работают корректно.

Город хранить только как подтверждённое поле организации/профиля с источником, если его сейчас нет — добавить разрешённое редактируемое поле и unknown в старых данных. Не угадывать город по БИН/телефону. Для фильтра «преподаватель» зафиксируй семантику: действующая учебная связь или фактический преподаватель события/проверки; историческую атрибуцию не подменяй текущей связью.

Используй текущий enrollment-query/scope и отдельные необходимые агрегаты; не загружай всю БД в Node/браузер ради одного счётчика. Нужны индексы по реальным query plans, стабильная сортировка с tie-breaker, bounded pagination и отсутствие N+1 на типовых страницах. Кэш допустим лишь с tenant/scope/фильтрами и корректной инвалидацией.

12. N07 — ВОСЕМЬ ВИДОВ ОТЧЁТОВ И ТРИ ФОРМАТА

Основание: TZ-48-01, §48 ¶1061–1076. В этой волне выполнить локальную отчётную часть целиком, не объявлять один CSV полным разделом.

Обязательные виды:
1) по обучению;
2) по сотрудникам;
3) по тестированию;
4) по документам;
5) по организациям;
6) по срокам;
7) реестр удостоверений;
8) реестр сертификатов.

Для каждого — осмысленная схема колонок/итогов, scope, фильтры, определение строк и дата среза; экспорт PDF, Excel/XLSX, CSV. Переиспользуй существующие CSV/XLSX, приватное хранение и очередь/renderer. Общая архитектура отчётов допускается; не нужны 24 независимых генератора или 24 новых capability только из произведения типов и форматов.

Различай отчётный срез и юридический документ. PDF отчёта не получает фиктивную подпись/официальную силу. Реестры используют реальные типы/статусы существующих issuance; наличие строки в историческом отчёте об аннулировании не разрешает скачивание отменённого оригинала.

Срез должен быть воспроизводим: фиксируй filters, scope policy, requesting actor, timestamp и согласованную модель данных/ревизий. Список/count/summary/export сравнивай на одной фиксированной выборке. Для длительной выгрузки не полагайся только на timestamp, если между страницами меняются данные: выбери snapshot/materialization или доказуемый эквивалент. Поясни выбранную семантику.

Малые отчёты допускают непосредственное формирование; большие — durable async job с прогрессом/ошибкой/retry, bounded RAM/чанками и приватным файлом. Не держи длительную транзакцию без необходимости. Повтор нажатия не плодит одинаковые задания; отмена/истечение retention очищают только принадлежащие этой операции временные файлы. Политика хранения тестовая/локальная, не выдуманный юридический срок.

Авторизация проверяется при создании, в worker и при скачивании. Готовый приватный URL не должен пережить отзыв полномочий с утечкой. Старый job не получает новые права из query параметров. Поддельный jobId/fileId или фильтр чужой организации не расширяет область.

Проверь пустой отчёт, длинные ФИО/названия, кириллицу/казахские символы, даты/timezone, многостраничный PDF, повтор заголовков/переносы, отсутствие обрезания важных колонок. CSV/XLSX защищены от formula injection, сохраняют идентификаторы/ведущие нули, не превращают строковые коды в числа. Сверь значения и итоги программно и просмотри реальные PDF-страницы. Реальную физическую печать не заявляй.

13. N08 — ЛОКАЛЬНАЯ 2FA И ЗАЩИТА НОВЫХ ПУТЕЙ

Основание: TZ-51-02, §51 ¶1125; необходимая часть TZ-51-01, ¶1121–1134; audit TZ-39-01, §39 ¶860–885.

Реализуй рабочую локальную 2FA без внешней SMS/email-службы. TOTP с recovery codes — ENGINEERING_DECISION, а не буквальное название механизма в исходном ТЗ. Используй проверенную доступную реализацию стандартного алгоритма, существующую auth/session инфраструктуру и защищённое хранение; не пиши собственную криптографию.

Путь: настройки безопасности → недавняя повторная проверка пароля или эквивалентный подтверждённый re-auth → setup secret/QR → подтверждение правильным кодом → включение → последующий password login → ограниченный challenge → полноценная сессия только после второго фактора. Одна обычная действующая сессия без недавнего re-auth не разрешает завершить первоначальный setup. Замена уже включённого фактора требует также действующего второго фактора либо предусмотренного recovery. Давность и назначение re-auth проверяются сервером. Неподтверждённый setup не включает 2FA. Секрет и recovery codes показываются только в нужном защищённом контексте, без логирования и кеширования.

Для привилегированных ролей предусмотрена явная локальная политика обязательности. При включении политики уже существующие непрошедшие 2FA сессии не должны сохранять обход staff API. При этом не блокируй молча весь существующий preview: подготовь отдельные synthetic users/профиль, безопасный setup/recovery и явно опиши миграцию политики. Старых пользователей нельзя автоматически объявить зарегистрировавшими второй фактор.

Ограниченная challenge-сессия не получает staff/learner данные, файлы, exports или возможность повышать роль. Проверки серверные, защищены от CSRF там, где используется cookie auth. Rate limiting — по подходящему сочетанию account/challenge/IP; не блокируй весь офис из-за одного пользователя и не разрешай обход сменой IP.

Защита от replay одного TOTP timestep, от повторного recovery code и гонки двух запросов — атомарная. Recovery codes случайные, в хранилище только проверяемые хеши, одноразовые; повторная генерация отзывает старые. Seed шифруется существующим/обоснованным локальным key mechanism с версией ключа; без ключа fail-closed, не hardcoded fallback. Не включать реальные secrets в Git/evidence.

Отключение/сброс требует подтверждённых прав и недавней проверки; после изменения учитывай session revocation. Для потери устройства — явный безопасный recovery path с audit, без публичного unauthenticated reset и без превращения knowledge of e-mail в доказательство личности. Не создавать скрытый bypass для прохождения тестов. Ротацию ключа и необходимость ключа при restore описать честно.

Продолжи существующий audit: только новые реальные события заявки/импорта/заказа/назначения/уведомлений/отчёта/2FA, actor/time/object/correlation и безопасный before/after. Не выдумывать ретроспективный IP или историю. Подтверди доступность audit уполномоченной роли и отсутствие у работодателя/слушателя чужих событий.

2FA и локальная защита не означают готовую production security: HTTPS, площадка, реальные ключи, эксплуатационные процедуры и юридическая приёмка отдельно.

14. N09 — ПРОИЗВОДИТЕЛЬНОСТЬ, ВОССТАНОВЛЕНИЕ И ОБЪЕДИНЁННАЯ ПРИЁМКА

Основание: TZ-01-02, §1 ¶41–43; необходимая локальная часть TZ-51-01/03; §73 архитектура. Это пакет реализации найденных ограничений и доказательств, не пункт «просто запусти один load test».

До оптимизаций зафиксируй воспроизводимый synthetic workload, размер данных, железо/runtime, настройки worker, измеряемые операции и инженерные бюджеты. Нельзя выбрать критерии после получения удобного результата. Не меняй business rules ради throughput.

Минимальные данные: две tenant; минимум две организации в одной tenant; новые и известные люди, неоднозначные строки, разные роли, курсы/версии/группы, текущие и исторические результаты, разрешённые/ожидающие/отменённые/заменённые документы, неизвестные и известные сроки. Набор не менее 1 000 сотрудников/назначений; отдельная проверка списков/экспортов на 5 000 строк или честно зафиксированный предел машины. Один bulk сценарий обязательно больше размера страницы и рабочего чанка.

Для уже существующих путей измерь baseline и итог на одинаковом workload и данных. Для новых ещё отсутствующих операций baseline обозначается NOT_AVAILABLE, без выдуманной нулевой задержки или процента улучшения; заранее зафиксируй их инженерные бюджеты и проверь итог после реализации. Разделяй сопоставимое before/after существующего набора и итоговую ёмкость расширенного набора. Проверяемые операции: list/filter/count/summary, autosave, импорт/назначение, inbox/reminders, отчёт, очередь документов и Range чтение. Не исполняй их только по очереди, нужен смешанный прогон. Ступени конкурентности, например 1/10/25/50 виртуальных клиентов, длительность steady phase не менее 60 секунд на проверенную ступень после прогрева; точный план и безопасные stop thresholds зафиксировать до запуска. Это локальная инженерная методика, не численная норма DOCX.

Собери latency p50/p95/p99, throughput, ошибки по операциям, timeout/retry, длину/возраст очереди, CPU/RAM процесса, query count и планы горячих запросов. Отдельно отмечай ramp/прогрев/steady и ресурсные ограничения. Если машина упёрлась в потолок, сохрани измеренный предел и незакрытую часть capacity; не называй это внешним сервисным блокером и не утверждай тысячи concurrent users по числу строк в БД.

Исправь воспроизводимые N+1, unbounded чтения/материализации, утечки памяти/файлов, конфликты соединений, отсутствие backpressure и неидемпотентное выполнение в выбранном контуре. Индексы должны иметь измеряемую пользу/объяснение плана. Не внедряй Redis/Kafka/микросервисы просто ради названия «масштабирование». Критерий отсутствия N+1 проверяй ростом данных, а не произвольной сменой магического query budget.

Проверь interrupt/restart собственных workers на середине batch/report/notification: законченное не повторяется, незавершённое восстанавливается, lease истекает корректно, частичные файлы не выдаются готовыми. Не убивай чужие процессы и работающий пользовательский preview ради fault injection.

Локальная резервная копия и restore: synthetic БД + необходимый private storage + безопасное описание зависимостей от ключей → новая отдельная БД/каталог → проверка ссылочной целостности, хешей файлов, unread/read inbox, продолжения job, 2FA входа и доступности разрешённого документа. Зафиксируй фактическое время и объём; это measured local recovery, не production RPO/RTO. Исходная БД и файлы не изменяются/не удаляются. Проверка только БД без файлов/ключей недостаточна.

Обязательный объединённый путь:
заявка/заказ → назначение → существующие обязательные материалы/промежуточная проверка → принятая ревизия практической работы → ручной ответ и решение уполномоченного проверяющего → eligible result → consumption существующего outbox → штатный документный workflow → renderer → разрешённое скачивание → отражение в заказе/inbox/отчёте.

В этой цепочке используй синтетическую программу с явно допустимым уже поддерживаемым документным правилом и необходимыми существующими approvals. Если шаблон допускает отсутствие подписантов — это явное свойство synthetic fixture, не обход подписи. Не меняй производственные/санитарные правила ради файла. Для несовместимого/требующего реальных полномочий правила должен сохраняться корректный отказ. Внешний санитарный provider остаётся NOT_CONNECTED.

Отдельно сохрани обычный DEMO путь: подготовка/штатное согласование/очередь/PDF-DOCX/допустимый комплект. Проверка обычной печати не подменяет LMS цепочку. Отмена/замена выдачи закрывает nonstaff original/bundle и не делает исторический отчёт ложным.

15. ОРКЕСТРАЦИЯ И ПОРЯДОК

Сначала общая короткая сверка остатка, baseline и соглашения, затем реализация. Не открывай бесконечную фазу исследования. Одновременно работай не большим числом агентов, чем доступно.

Оркестратор владеет schema/migrations, shared contracts, auth/policy/scope, root integration, runtime профилем и финальным evidence. Перед параллельными правками зафиксируй API/DTO, transition semantics, idempotency, migration dependencies и владельцев общих файлов. Агенты не редактируют одновременно schema.prisma, общий controller, auth.ts, shared types, workspace navigation, общие locale dictionaries или package/lock files.

Рекомендуемое разделение при трёх sub-agents:
A — N01/N02: каталог, заявки, очередь и связь существующего заказа.
B — N03/N04: employer import/assignment и рабочие кабинеты.
C — N06/N07: единые определения/выборки, сводки и отчёты.
Оркестратор — N05/N08/N09 и интеграция. После окончания независимого пакета передай свободному агенту адресную независимую проверку чужой вертикали. При другом числе slots сохрани те же границы владения.

Зависимости:
- baseline/контракты/схема → вертикали;
- N01/N02 и N03 используют один разрешённый assignment path;
- N04 собирает реальные результаты N01–N03/N05/N06/N07;
- N05 сначала контракт событий, затем подключение их в транзакциях владельцами вертикалей;
- N06 определения/фильтры → N07 отчёты;
- N08 auth change согласуется с fixtures всех веток до browser run;
- N09 baseline нагрузки до оптимизаций; единая приёмка после интеграции.

Агенту передавай абсолютную рабочую директорию, область/файлы, критерии, зависимости и local-only ограничения. Его финальный текст не равен PASS: оркестратор сопоставляет код, команды, fixture IDs и evidence. Не принимай stale successful build другой рабочей копии.

На каждом значимом этапе оставляй компактный checkpoint: что сделано, кто владеет файлами, миграции, что запущено, exact next step. Если контекст сжат, продолжай по checkpoint без повторной реализации. Пользователю сообщай конкретный результат и оставшуюся неопределённость, не каждый внутренний tool call.

16. UX И ЛОКАЛИЗАЦИЯ — ЧАСТЬ ПРИЁМКИ

Сохраняй существующий визуальный язык DEMO, компактные списки, autosave, keyboard и bulk. На текущем шаге одно основное действие и не более одного конкурирующего вторичного. Не заставляй повторно вводить известные данные, выбирать уже известную организацию/курс/группу или проходить лишний CRM-этап ради обычной печати.

Для подготовленных повторных операций назначения/получения готового результата целевой предел — до двух действий; продолжить своё обучение — одно. Подготовку, первый ввод, настройку импорта/2FA, разрешённые подтверждения и исправление неоднозначностей измеряй отдельно. Два CTA на экране не доказывают две операции по всему пути.

Первичная настройка 2FA и подтверждение намеренного массового импорта обоснованны; повторяющийся бессодержательный confirm на каждой строке — нет. Секреты/правовые основания/экзамен нельзя подделывать ради уменьшения кликов.

Новые строки UI и ошибки RU/KZ. Не заявляй профессиональную проверку всего существующего перевода; проверяй добавленное/изменённое. Смена языка не теряет ввод, таблицу сопоставления, выбор, фильтры и комментарий.

Ошибки 400/403/409/429/503/обрыв соединения отображаются по месту и предлагают реальное восстановление. «Сохранено» только после подтверждения сервера. Поздний initial GET не перетирает ввод. Reload/retry не дублируют отправку или job.

Доступность клавиатурой Tab/Enter/Escape, видимый focus, понятные подписи, достаточные hit areas, отсутствие важных hover-only действий. Проверка 360/390/768/1440, длинные RU/KZ строки и таблицы; горизонтальное прокручивание разрешено там, где таблица действительно требует его, но primary action и ошибки остаются доступны.

В UX_ACTIONS.json сохраняй по реальному browser-сценарию: роль/fixture, предусловия, действия, введённые и повторно введённые поля, решения, диалоги, ручные refresh, восстановление, viewport и результат. Время измеряй только реальным таймером, иначе NOT_MEASURED. API seed и подготовку не выдавай за действия пользователя; synthetic script не объявляй исследованием удобства реальных людей.

Для каждой строки фиксируй PASS/FAIL/PARTIAL/NOT_RUN/BLOCKED_EXTERNAL_INPUT, свежий evidence, команду/URL/fixture, уровень проверки, конкретное ограничение. PASS только после исполнения на фактическом итоговом дереве. Частичное исходное требование не становится полным из-за PASS более узкого AC.

19. ПРОВЕРКИ И ДОКАЗАТЕЛЬСТВА БЕЗ ПОДМЕНЫ РЕЗУЛЬТАТА

Нужны адресные unit/contract проверки новой семантики, интеграция с реальным локальным PostgreSQL, реальные browser пути, рендер отчётов/документов и scoped негативные случаи. После исправления повторяй затронутые проверки; не делай много полных повторов без новых изменений.

Миграции: свежая БД и обновление сохранённой до проходки synthetic копии. Проверь старые данные, 2FA disabled/default, прежние SESSION уведомления и действующие правила доступа. Новые defaults не должны изменить смысл исторических строк.

Проверь новые PDF визуально через доступный локальный renderer/viewer, таблицы программно. При работе с реальными PDF/Office артефактами следуй доступному профильному skill, если он применим. Не объявляй физических распечаток без факта печати.

Evidence хранит synthetic IDs, команды, время, source hashes и результаты, но не секреты. Raw traces, HAR, DB dumps, cookies, OTP setup и приватные файлы оставляй в .runtime; в docs/evidence — очищенные выдержки, хеши и ссылки. Проверь утечки секретов перед сдачей.
