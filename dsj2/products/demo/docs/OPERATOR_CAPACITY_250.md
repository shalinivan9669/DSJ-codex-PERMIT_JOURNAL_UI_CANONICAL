# Вместимость операторской заявки: 250 получателей

Дата проверки: 29.09.2026. Область: автономный DEMO в ветке `codex/ot-center-dsj-forms-ux`. Проверки выполнены локально на синтетических данных; рабочая БД и production не изменялись.

## Решение

Вместимость одной заявки увеличена со 100 до **250 получателей**. Это согласованное ограничение редактора, контрактов API, PostgreSQL, импорта и Python-рендера. Заявки на 100 человек продолжают обрабатываться. При 251 строке исходный файл остаётся виден полностью: оператор явно исключает лишние строки либо делит список на заявки. Автоматического обрезания нет.

Увеличение до 500 не сделано. Для текущей задачи достаточно 250, а для следующего увеличения нужны самостоятельные измерения интерфейса, сохранения, массовых операций и полного выпуска.

## Изменения

- `LIMITS.rows = 250` управляет Zod-схемами черновика, API импорта и сверки списков, доступностью добавления получателей и проверкой диапазона вставки.
- Новая миграция `202609290015_request_capacity_250` увеличивает PostgreSQL CHECK `request_rows` до 250. Историческая миграция с ограничением 100 сохранена без изменений.
- Python использует единый `MAX_REQUEST_ROWS` в импорте, индивидуальном DOCX и общем протоколе. Сообщения импорта возвращают фактический лимит 250.
- Вставка диапазона следует видимому порядку колонок. В режиме RU три колонки означают ФИО, должность и место работы на русском; существующие KZ-поля сохраняются. Режим RU + KZ использует видимые пары. Предпросмотр показывает порядок полей перед применением.
- Проверки границ обновлены на 250/251; проверки совместимости 100 сохранены.

## Ограничения, которые сохранены

| Ограничение                   | Значение и причина                                                                                                                                                   |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| JSON запроса                  | 2 МиБ в API и web proxy. Изменение вместимости не снимает защиту размера запроса.                                                                                    |
| Документы в выпуске           | До 1000. Несколько документов на одного человека и общие протоколы учитываются отдельно.                                                                             |
| Назначения одному человеку    | До 10.                                                                                                                                                               |
| Импортируемый файл            | До 5 МиБ в API. Защита XLSX от формул, макросов, внешних ссылок и архивных бомб сохранена.                                                                           |
| Один пакет сопоставления фото | До 100 файлов и 50 МиБ суммарно. Для 250 человек фотографии загружают несколькими пакетами.                                                                          |
| Рендер                        | Таймаут Python по умолчанию 120 секунд; PDF-конвертера 180 секунд; внешний PDF-процесс 210 секунд. Таймауты и ресурсы не повышены.                                   |
| Перенос исторических данных   | Ограничение 100 в `scripts/migration/import-legacy.ts` сохранено как отдельный контракт переноса старых заявок; этот путь не используется новым операторским вводом. |

Измеренный JSON обычной двуязычной заявки с 250 заполненными получателями и одним назначением на каждого занимает **330080 байт для рабочих** и **322569 байт для ИТР** из 2097152 допустимых байт. Измерение выполнено через реальные `newRequestBundle`, `recipientForRequest` и `draftSchema`; фото передаются ссылками. Это не гарантия для любых 250 строк с максимальными 500-символьными полями и десятью назначениями: такие данные по-прежнему могут достичь ограничения размера.

Группа Python-проверок протоколов завершилась за 228.319 секунды суммарно; это время нескольких десятков файлов, не одного рендер-задания. Пример PDF и проверка содержимого: `docs/evidence/operator-value/group-layout/ptm-protocol-250.pdf` и `ptm-protocol-250-verification.json`.

Дополнительно `test_request_capacity.py`: **2 теста PASS за 45.020 секунды**. Реальные XLSX и TSV сохраняют все 250 строк, независимые RU/KZ и ведущие нули; при 251 строке возвращают полный исходный список и ограничение. Индивидуальный DOCX содержит все 250 участников ровно по одному и в исходном порядке; при 251 участнике выходной файл не создаётся.

Повторная проверка `tests/integration/import-delivery.test.ts`: **8 тестов PASS за 44.089 секунды**. Исходный исторический fixture на 100 человек сохранён: его пересмотр теперь законно даёт 102 строки без исключения отсутствующих. Отдельная синтетическая заявка проверяет границу сверки 249 + 2 = 251: отказ сохраняет предыдущую редакцию и не записывает idempotency-операцию; явное исключение одного отсутствующего участника позволяет сохранить ровно 250. Прежние проверки исключения, повторного применения, tenant isolation, реестра, 100 фото и контрольного PDF прошли.

Изменён сценарий браузерной проверки `demo.spec.ts`: 251 исходная строка → явное исключение одной → 250 строк → сохранение/reload → безопасный повторный импорт. Само изменение теста не является PASS браузерной проверки; её результат фиксируется отдельно в общей приёмке интерфейса.

## Границы подтверждённого результата

Проверены вместимость и сохранность данных, импорт и фактические печатные файлы. Полный выпуск 250 персональных удостоверений вместе со всеми архивами, UX-время заполнения оператором, все браузерные сценарии и физическая печать этим отчётом не подтверждаются. Старые результаты выпуска 100 человек не заменяют эти проверки.

Для обновления реального окружения требуется отдельно авторизованное применение новой миграции вместе с версией приложения. После появления заявок с более чем 100 получателями откат к старому приложению с прежней Zod-схемой потребует отдельного плана совместимости.
