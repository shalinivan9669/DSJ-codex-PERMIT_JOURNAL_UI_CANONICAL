# Подключение ЭЦП НУЦ РК и eGov Mobile

Техническая памятка администратору. Проверено по исходникам и официальной документации 8 ноября 2026 года. Настройка адресов сама по себе не доказывает работоспособность внешних сервисов.

Проверка действующего сайта 8 ноября 2026 года в 18:55:15 UTC: авторизованный `GET signing` вернул HTTP 200; `NCALAYER.available=false` (не подключён сервер проверки НУЦ), `EGOV_QR.available=false` (не подключены eGov и сервер проверки). Сессия завершена штатным выходом; документы не подписывались и не изменялись. Санитизированное свидетельство: `.runtime/ui-copy-audit/live-signing.json`. Описанные исправления клиентского запроса не заменяют отсутствующие сервисы.

## Что уже реализовано

- Единый путь для обычных выпусков и протоколов комиссии LMS: точный PDF → назначенный подписант → CMS → независимая серверная проверка → сохранение подписи и её доказательств. LMS использует тот же модуль, отдельное подключение не требуется.
- Браузер обращается к NCALayer на компьютере подписанта: `wss://127.0.0.1:13579/`, `kz.gov.pki.knca.basics/sign`. Передаётся PDF в Base64, запрашивается откреплённый CMS и сертификат для подписи (`1.3.6.1.5.5.7.3.4`). Параметр `chain` не передаётся: сохраняется штатная проверка действующих сертификатов НУЦ РК.
- API проверяет неизменность PDF, полномочия пользователя и замороженное назначение подписанта; затем сверяет ответ проверяющего сервиса с SHA-256 файла и ИИН/БИН назначения. Подтверждение на бумаге не создаёт ЭЦП.
- Для eGov предусмотрен серверный адаптер создания сессии и получения CMS. Описанные ниже `/sessions` — контракт нашего адаптера, **не адрес публичного API eGov**.

В продукт не включён криптопровайдер НУЦ РК или готовый сервер криптографической проверки. Включение переменных окружения не создаёт такой сервис. Не следует направлять документы в произвольный публичный сервис проверки.

## Что предоставить для подключения

1. Для NCALayer достаточно проверяющего сервиса — eGov не обязателен. Нужны либо согласованный сервис с адресом и доступом по контракту ниже, либо официальный комплект разработчика НУЦ РК для развёртывания собственного сервиса. НУЦ направляет владельца ИС/представителя на получение SDK; публичный `sdkinfo` содержит документацию, но не сами библиотеки.
2. Для eGov Mobile дополнительно нужны доступ к интеграции eGov Mobile QR и её актуальная документация/параметры, предоставленные для этой ИС. Официальный каталог Smart Bridge содержит сервис `EGOVMOBILE_QR_SIGN_SERVICE`, `NITEC-S-5096`, владелец АО «Национальные информационные технологии». Наличие приложения eGov у пользователя не заменяет подключение информационной системы.
3. Директор назначает действующих пользователей в роли подписантов с правильными ИИН и, когда требуется назначением, БИН. Для уже выпущенного документа изменение настроек не переписывает зафиксированные полномочия: используется штатное исправление/новый выпуск.
4. Для проверки NCALayer подписант запускает актуальный NCALayer на своём компьютере и использует собственный действующий ключ. Ключ и пароль остаются у подписанта. Для eGov он самостоятельно подтверждает действие в приложении.

Первое подключение проверяют на отдельном согласованном документе. Запись о проверенной ЭЦП появляется только после настоящего подписания и успешной серверной проверки. Тестовые RSA-сертификаты из integration-тестов не являются сертификатами НУЦ РК и не доказывают готовность production.

## Серверные переменные

Только в окружении API; не в `NEXT_PUBLIC_*`, браузерном коде или репозитории:

| Назначение | Переменные |
| --- | --- |
| Проверка CMS; обязательна для обоих способов | `DEMO_SIGNATURE_VERIFIER_URL`, `DEMO_SIGNATURE_VERIFIER_TOKEN` |
| Адаптер eGov Mobile; дополнительно для QR | `DEMO_EGOV_SIGNING_CONNECTOR_URL`, `DEMO_EGOV_SIGNING_CONNECTOR_TOKEN` |

URL должен быть HTTPS, без встроенных учётных данных, query и fragment. API добавляет путь к базовому URL и передаёт `Authorization: Bearer <token>`. Переадресации запрещены, таймаут запроса — 20 секунд. Исключение HTTP loopback существует только при `NODE_ENV=test` для изолированных тестов.

## Контракт проверяющего сервиса

`POST /verify/cms-detached`, JSON:

```json
{
  "documentBase64": "<точные байты PDF в Base64>",
  "signatureBase64": "<откреплённая CMS в Base64>",
  "expectedAuthority": "NCA_RK",
  "checkRevocation": true
}
```

Успешный JSON-ответ строго соответствует схеме:

```json
{
  "valid": true,
  "authority": "NCA_RK",
  "chainValid": true,
  "revocationStatus": "GOOD",
  "revocationCheckedAt": "<ISO datetime>",
  "purpose": "SIGNATURE",
  "contentSha256": "<64 строчные hex-цифры>",
  "signerIin": "<12 цифр>",
  "signerBin": null,
  "certificateSerial": "<серийный номер>",
  "certificateFingerprint": "<SHA-256, 64 строчные hex-цифры>",
  "notBefore": "<ISO datetime>",
  "notAfter": "<ISO datetime>"
}
```

`signerBin` можно опустить, передать `null` или 12 цифр. Все поля должны быть получены из реальной криптографической проверки CMS и сертификатов, а не скопированы из запроса. Нужны поддержка актуальных алгоритмов НУЦ, доверенная цепочка, назначение ключа, срок сертификата и проверка отзыва с закрытым отказом при неопределённости. API дополнительно требует актуальность результата отзыва не старше пяти минут, действующий срок сертификата и совпадение PDF/подписанта. Отрицательный результат нельзя выдавать как `valid:true`.

Для собственного сервиса нужны официальный SDK, правила проверки НУЦ, доверенные сертификаты, доступ к OCSP/CRL и согласованный защищённый адрес. Клиентский NCALayer не заменяет серверный криптопровайдер. Общедоступные OCSP/CRL НУЦ проверяют статус сертификата; сами по себе они не являются нашим `/verify/cms-detached`.

## Контракт адаптера eGov

`POST /sessions`: `sessionId`, `documentBase64`, `documentSha256`, `format:"CMS_DETACHED"`, `signerIin`, `signerBin`, `expiresAt`. Сессия приложения действует 15 минут.

Ответ: `id` (идентификатор адаптера), `signingUrl` и/или `qrUrl` — HTTPS-ссылка для подписания. Интерфейс показывает QR этой ссылки. Это должна быть ссылка пользовательского подписания, а не URL PNG-картинки QR.

`GET /sessions/<id адаптера>` после подтверждения пользователем возвращает `sessionId`, `documentSha256`, `status:"SIGNED"`, `signatureBase64`. Идентификатор и хэш должны совпасть с исходным запросом. Пока подписи нет, адаптер не возвращает успешный ответ `SIGNED`; текущий API трактует неуспешный HTTP-ответ как отсутствие подтверждения. Сохранённая сессия позволяет проверить ещё раз. Полученный CMS всё равно проходит общий независимый verifier; сам QR и статус стороннего сервиса не считаются подписью.

## Проверка подключения

- Под учётной записью сотрудника `GET /api/print-requests/:id/signing` показывает `providers` без токенов. `available:true` означает наличие корректно заданных адресов и токенов, а не успешную проверку внешнего сервиса.
- Проверить собственный сервер/сервис на корректной CMS и отказах: изменённый PDF, другой ИИН/БИН, недействующая цепочка, отозванный/просроченный сертификат, недоступность OCSP/CRL. Выполнить реальную контрольную подпись NCALayer; для eGov — отдельно полный путь QR → подтверждение → проверка CMS.
- Проверить сохранение доказательств и повтор запроса без дубликата; обычный выпуск и LMS должны использовать те же провайдеры. Не обходить отдельную настройку допуска LMS к реальным данным.
