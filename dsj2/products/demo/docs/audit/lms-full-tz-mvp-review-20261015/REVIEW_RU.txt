2. Что именно означают оценки

Принадлежность и состояние независимы. Использованы:
- подтверждено / частично / отсутствует / недостаточно доказательств;
- обязательное для согласованного MVP / дополнительное требование полного ТЗ / внешнее условие / новая рекомендация / неоднозначность.

«Подтверждено» означает наличие локального процесса по актуальному коду и соответствующих сохранённых доказательств. Это не новая исполнительная приёмка и не утверждение о production. «Отсутствует» применяется только к функции, для которой после проверки модели, API и UI не найден полноценный путь. «Недостаточно доказательств» применяется, например, к реальной мощности и утверждённым профессиональным программам.

Матрица содержит 117 строк рассмотрения, все 76 разделов, плюс отдельно санитарный согласованный объём и новые инженерные рекомендации. Это не 117 уникальных функций: сводные разделы 69–76 сохраняют ссылки на уже рассмотренные процессы, а не увеличивают объём реализации. Самостоятельные требования разделены, однотипные поля одного объекта объединены с сохранением абзацев.

4. Подтверждённые пробелы и их реальное влияние

F1 — premature exam admission.
Math.round(100 × 199 / 200) = 100. exams.ts:177 использует это значение как разрешение на старт. UI повторяет вычисление в learn.tsx:263 и проверку :312. Точный final eligibility в result-finalization.ts:244–263 сохраняет запрет выдачи при незавершённом уроке. Исправление нужно для согласованности обучения, попыток и объяснимого результата, не для уже доказанного обхода выдачи.

F2 — editor recovery и версии вопросов.
course-editor.tsx:942–956 удаляет lesson, но оставляет его ID в prerequisiteLessonIds других уроков. Picker :896 показывает только существующие уроки; снять скрытую ссылку нельзя. validation.ts:84 блокирует publish. Нужно безопасное решение в контексте удаления, без молчаливого ослабления обязательного маршрута. Модуль и отдельный ответ должны удаляться без переписывания остальных данных; удаление правильного ответа требует явного нового выбора. Номер question revision должен назначаться сервером при смысловом изменении публикации, не каждым autosave.

F3 — язык ошибки.
common.tsx:236–237 делает русский fallback. ACCESS_EXPIRED (scope.ts:85), ошибки строк назначения (enrollments.ts:187–199 → assignments.tsx:325) и подготовки документов (document-bridge.ts:200 → results.tsx:431) обходят перевод. Нужен общий кодовый контракт. Файлы — отдельное расширение следующего этапа: общий двуязычный materialId уже допустим; разные PDF полезны при наличии переводов. Разные видео требуют отдельной модели прогресса: объединять интервалы по одинаковым секундам без соответствия таймлайнов нельзя. Эту сложность в первую проходку не включать.

F4 — доказуемость изменения.
AuditEvent/audit() не имеют IP. courses.ts:148/158 обновляет draft profile/content, событие :166 содержит только revision. Добавлять доверенное происхождение запроса и минимальный diff значимых полей, исключая секреты/закрытые файлы. Старые неизвестные IP/before-state не восстанавливать догадкой.

Отдельный обязательный UX-остаток большого пакета:
document-bridge.ts:755 возвращает BUNDLE_LIMIT при >64 MiB с просьбой выбрать меньшую часть. Это ограничение фактически достижимо по коду; нового воспроизведения с большим архивом не проводилось. Для A1/S1 нужна автоматическая разбивка/очередь с общим выбранным набором, а не ручная работа по подгруппам.

6. Масштабирование без смены архитектуры

Функциональное расширение и производительность — разные задачи. Зарегистрированные тысячи пользователей сами по себе не означают тысячи одновременных экзаменов, видео и рендера.

Первичное сохранённое измерение:
docs/evidence/lms-one-run-20261015/agent-c/load-1792017682452.json:1–20
100 synthetic users, 100 enrollments, 1 course, 400 read/autosave HTTP, observedInFlight=100, p95=799.1326 ms, unexpected5xx=0; длительность 2901.5534 ms. Машина i5-11400H, 12 logical CPUs, около 34.1 GB RAM.
Это burst около 2.9 секунд. Он не измеряет длительную нагрузку, видео, массовое завершение экзаменов, рендер и тысячи одновременных пользователей. Отдельное доказательство 250 назначений не делает 10000 назначений доказанной ёмкостью.

Конкретные ограничения:
1) auth.ts:79 ограничивает API по req.ip 600/min. За Next proxy клиентский IP не передаётся (app/api/[...path]/route.ts:28–40); trusted proxy не настроен. Пользователи могут делить один bucket. S1: раздельные authenticated session/user budgets и безопасная proxy policy; login остаётся отдельным. Не просто увеличить число.
2) courses.ts:55–74 делает pagination до published filtering плюс N+1 latest version/profile. S1: фильтрация/count на одном eligible наборе, batch fetch, лёгкая проекция, стабильная сортировка.
3) document-bridge.ts:624–629 сначала читает все enrollment IDs, затем results page и per-row events/links/documentView (:641–665). S1: ограничить до страницы и batch projections. Enrollment list также проверять по составу выбранных данных, не называть весь продукт «без пагинации».
4) validation.ts:25 разрешает 10000 recipients, enrollments.ts:160–237 обрабатывает их последовательно в одной транзакции; core.ts:151–154 timeout 30s. S1: внутреннее ограниченное дробление/возобновление и итог строк. Пользователь не режет группу вручную; пределы не становятся новым бизнес-лимитом 250.
5) materials.ts:197–215 хэширует весь файл до каждого Range, затем отдаёт диапазон. Файл до512 MiB уже стримится, но disk I/O повторяется на seek. S1: контроль целостности неизменяемого blob с валидируемым кешем/инвалидацией и периодической проверкой, без доверия одному размеру файла.
6) LMS material upload не входит в concurrency guard photos/imports (auth.ts:143–156). Ограничить одновременно принятые крупные загрузки/временный диск и cleanup, не обычные действия оператора.
7) Большой download >64 MiB сейчас требует меньшего набора. Использовать существующие multipart/archive механизмы и durable job при необходимости, не держать весь большой набор в памяти.
8) В source deployment не задан общий бюджет Prisma connections по API/render/integration replicas. До добавления процессов зафиксировать pool budget. Нет доказательства, что pool уже исчерпан. Индексы tenant/status/deadline/outbox/idempotency есть; новые индексы выбирать по конкретным будущим EXPLAIN, не массово наугад.

Очереди:
render queue.ts:16–45 имеет SKIP LOCKED/lease/fencing, main.ts:23–25 concurrency по умолчанию2, допустимо1–4; старый deferred ZIP учитывается FIFO. tests/integration/queue-fairness.test.ts:9 доказывал один tenant, не справедливость между центрами. Межtenant quotas — следующий этап общей установки, если измерено соседское влияние.
Sanitary outbox транзакционно создаётся с результатом; preparation.ts имеет lease/retry/immutable batch; delivery.ts:302–324 различает UNKNOWN и безопасную сверку. Shipping worker не отправляет провайдеру. Слепой повтор запрещён.
Очень большие ZIP parts могут одновременно удерживаться в renderedParts/additionalOutputs (render-worker/queue.ts:125–153). Последовательная запись частей — следующий шаг при росте архивов; A1 не должен расширять этот риск без границы.

Поставка:

- readiness в api/controller.ts:76–97 смотрит renderer, integration heartbeat отсутствует.

Серверный deadlineAt и проверки времени при чтении/отправке попытки сохраняются независимо от worker.

7. Следующие пункты общего ТЗ

Следующий этап после первой проходки, по порядку:
1. Учебная полнота под подтверждённые программы (§4/10/11/34–36/69): промежуточные quizzes, практика с работой слушателя и ручной оценкой, минимальные capabilities преподавателя/методиста/эксперта, затем соответствующие типы вопросов. PRACTICE не становится официальным VerifiedExamResult.
2. Управление актуальностью и группами (§27–29/32/54–56): ответственный и дата проверки НПА, карта затронутых программ, пауза новых назначений; отдельное решение для уже начатых курсов. Полная группа с преподавателем/датами, межкурсовые prerequisites и более сложные окна доступа только по потребности.
3. Закрытие самостоятельного intake (§3/30–31/43–45/69): learner read-only каталог → запрос доступа в существующую заявку; employer предлагает новых сотрудников через существующее reconciliation. Не давать самозачисление или объединение людей по одному ИИН без решения владельца.
4. Коммерческая связность (§43–46): provenance от existing order/request к enrollment, затем недостающие стадии КП/договора/счёта/акта. Эквайринг после выбора провайдера.
5. Вебинары/посещение/календарь (§7/42/71), затем внешние уведомления (§41) при фактической пользе. Минимальный local webinar — событие, ссылка, преподаватель, ручное посещение с автором/датой; это не собственная ВКС.

2FA администратора (§51) — отдельный обязательный gate до открытого административного доступа с реальными данными. Это не основание сейчас усложнять всем слушателям локальный путь. При переходе к реальному использованию он важнее коммерческих дополнений.

Неоднозначности:
- Каталог для learner и self-service B2C: источник явно описывает выбор курса, согласованный запуск в основном реализовал управляемое зачисление. Для текущей B2B первой проходки допустимо отложить только с этой явной оговоркой. Если ближайший запуск объявляется самостоятельным B2C, минимальный «каталог → запрос доступа» становится обязательным до такого запуска.
- Employer Excel import: центральный импорт DEMO не равен самообслуживанию работодателя. Минимальный безопасный вариант — предложить состав на сверку центра, не создать дубль people.
- Промежуточные тесты/практика: крупные названия §75 не определяют все типы. Утверждённый прошлый MVP прямо ограничивал engine. Нельзя назвать всё дополнительное дефектом; нельзя запускать программу с обязательной практикой, которой продукт не умеет подтверждать.
- Полный нормативный справочник: версия profile уже решает историческую привязку; все реквизиты/monitor — отдельное расширение.
- Общий двуязычный файл допустим; раздельные assets нужны тем программам, где содержание реально различается.
