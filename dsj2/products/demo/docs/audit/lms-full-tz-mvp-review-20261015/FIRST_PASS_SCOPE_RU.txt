1. Решение об объёме

Первая проходка состоит ровно из восьми пакетов:
F1 точный допуск;
F2 исправимый редактор и достоверные ревизии;
F3 RU/KZ ошибок;
F4 полнота аудита;
S1 ограниченная ресурсоёмкость и пакетная работа;
S2 поставка/наблюдаемость integration-worker;
A1 рабочий список сроков/исключений, отчёт и готовый комплект;
A2 переиспользуемый банк вопросов.

F1–F4 — исправления обязательного MVP и его сквозных пользовательских путей.
A1–A2 — полезные дополнения общего ТЗ; отдельные ограничения существующего bulk download закрываются внутри A1/S1.
S1–S2 — минимальные инженерные меры роста и эксплуатации уже реализованного продукта.

Не включать весь §75 заново и не переписывать весь LMS. Главный результат: учебный путь и редактирование не имеют найденных тупиков, оператор управляет растущим числом людей из знакомого списка, методист переиспользует содержание, нагрузка ограничивается в конкретных дорогих местах.

Порядок:
1) F1.
2) F2; проект данных ревизий сразу согласовать с A2.
3) F3.
4) F4.
5) S1: сначала правильная выборка/счётчик каталога и ограничения запросов, затем файлы/пачки.
6) S2.
7) A1 поверх исправленных списков и пакетных ограничений.
8) A2 поверх исправленного versioning.

Независимые локальные части F3/F4 и S1/S2 можно выполнять параллельно после фиксации контрактов. Это не повод расширять набор. Prisma/shared contracts/guards должны иметь одного интегратора.

Относительные оценки S/M/L описывают объём затронутых поверхностей, не часы. Уверенность относится к границе и механизму, не к обещанию срока. Ниже все проверки — будущие, в исследовании они не выполнялись.

2. Исправить обязательный MVP сейчас

F1. Точный допуск к экзамену

Источник:
Полное ТЗ §9 ¶235–244, §10 ¶258–270, §20 ¶489–499; §75.9/10/12.
Согласованный TZ_LMS_MVP_RU.txt §5–6; L07/E02.
Состояние частично; функциональный дефект; уверенность высокая.

Что есть:
Серверный LessonProgress, immutable CourseVersion, оценка/попытки, точная финальная проверка eligible результата.
enrollments.ts:241–256 считает округлённый процент; exams.ts:177 использует 100 как gate.
learn.tsx:263/312 повторяет вычисление/условие.
result-finalization.ts:244–263 отдельно проверяет every required lesson.

Конкретный остаток:
Один точный предикат/проекция готовности по всем обязательным элементам вместо сравнения округлённого процента. Сервер возвращает UI готовность и краткую реальную причину блокировки. Процент остаётся показателем; до фактического завершения можно отображать максимум99 либо показывать точное количество — выбор не должен влиять на право начать экзамен.
Изменение охватывает старт и представление готовности; сохранить независимую финальную защиту результата.

Почему сейчас:
199/200 уроков дают100% и открывают экзамен. Пользователь может потратить попытку и получить PASSED без права на документ. Новый промежуточный quiz или dashboard этого не исправляет. Возможность незаконной выдачи этим исследованием не доказана.

Не входит:
Изменение оценки/порогов/количества попыток, массовая переоценка прошлых экзаменов, практика/прокторинг, новый engine.

Переиспользование:
LessonProgress, CourseVersion, финальная точная проверка, существующие reasons/learner buttons.
Данные: миграция не нужна; старые результаты не пересчитывать. Если выявлены реальные затронутые попытки, решение об их судьбе отдельно по фактам, без автоматического выдуманного PASS.

Зависимости/откат:
Независим от внешних входов. Версионно совместимый response можно расширить полем готовности.
Откат релиза сохраняет результатные данные; известный дефект нельзя считать безопасным рабочим fallback — при необходимости оставить gate fail-closed.

Объём S, риск низкий/средний, уверенность высокая.
Приёмка: один адресный набор 199/200 denied, 200/200 allowed, required/optional не смешиваются; UI и API согласны; final eligibility при незавершённом required по-прежнему false; повтор не расходует лишнюю попытку.
UX: +0 действий, +0 известных полей. Слушатель завершает реальный недостающий урок; причина показана рядом с основным действием.

F2. Исправимый редактор черновика и честная ревизия вопроса

Источник:
§4 ¶130, §5 ¶136–160, §12 ¶317–327; §75.5/6/11; L04/E01; UX03/08.
Состояние частично; функциональный дефект + незавершённый пользовательский путь.

Что есть:
CourseEditor/autosave/revision conflict; move-up; prerequisite picker; publish validation; immutable clone; вопросы/категории/snapshot.
course-editor.tsx:889–921, :924–1010, :1138–1236; validation.ts:58–134.
Удаление урока :942–956 оставляет его ID в зависимостях. Picker показывает только существующие уроки. У модуля и отдельного option нет удаления. Версия вопроса создаётся1, при правке не обновляется.

Минимальный остаток:
- Удалять ошибочный модуль, урок и вариант ответа без повторного ввода остальных данных.
- При удалении используемого prerequisite в том же контексте показать затронутые уроки и явное решение «убрать/заменить зависимость». Не очищать обязательный маршрут молча. Сохранить возможность отменить обратимое изменение до публикации.
- Ограничить picker допустимыми предыдущими уроками; после reorder дать исправимую адресную ошибку, без невидимой ссылки.
- Проверять RU/KZ названия модулей и показывать место ошибки.
- Сервер назначает новую question revision при изменении содержания в новой опубликованной версии; неизменённый вопрос сохраняет редакцию. Draft autosave не должен создавать сотни редакций. Клиент не назначает доверенный номер сам.
- Сохранить прошлый payload/snapshot и оценки без переписывания.

Почему сейчас:
Это повседневные операции подготовки курса. Без них методист пересоздаёт вопрос/курс или заполняет ненужный ответ; version=1 скрывает смысловое изменение. Новая библиотека вопросов без исправления ревизий закрепит проблему.

Не входит:
Drag & Drop, универсальный конструктор, новые типы вопросов, красивые анимации, автоматическая замена вопроса в начатом курсе.

Переиспользование:
CourseEditor, courseContentSchema/lmsQuestionSchema, updateVersion/publishVersion/cloneVersion, snapshot.
Данные: compatibility reader старых JSON; новая серверная ревизия только для новых изменений. Не угадывать одинаковость вопросов из разных курсов по совпавшему тексту.

Зависимости/откат:
До A2 зафиксировать стабильный question identity и revision. В старых snapshots не менять id/version/hash. Аддитивные поля/библиотечные ссылки nullable; при откате UI новые опубликованные snapshots остаются читаемыми.
Объём M, риск средний, уверенность высокая.

Приёмка:
Одна цепочка редактирования: зависимый урок → удаление/замена зависимости → удаление ошибочного модуля/варианта → publish. Остальное содержание и autosave не потеряны.
Одна цепочка версии: старый вопрос/попытка → новая смысловая редакция → публикация новой версии того же курса; прошлый набор вопросов и оценка прежние.
UI показывает конкретный модуль при пустом переводе. Проверки всех возможных сортировок не нужны.

UX:
Обычное редактирование получает0 новых обязательных экранов. Ошибочный вариант удаляется локально одним действием; значимое изменение зависимостей требует одного явного решения только в этом исключении. Экономия точных секунд/кликов не измерена и не обещается. Повторный ввод известного содержания0.

F3. RU/KZ в отрицательных пользовательских путях

Источник:
§50 ¶1100–1113, §75.24; L09/E12/UX07/08.
Состояние частично; подтверждённый функциональный дефект языка интерфейса.

Что есть:
Перевод основного UI, textRu/textKz, двуязычные вопросы, формы/документы.
common.tsx:236–237 возвращает errorText для неизвестного кода.
assignments.tsx:325–327 и results.tsx:431–434 показывают raw row message.
scope.ts:85 возвращает ACCESS_EXPIRED на русском.

Минимальный остаток:
Совместимый API error {code, params, message}; не терять code в batch errors.
Единый mapper RU/KZ для всех новых LMS пользовательских ошибок, включая expiry/invite/recovery/material/document/row failures. Не переводить автоматически свободный текст причины, введённый человеком.
Ошибка остаётся в контексте поля/строки; уже выбранные люди и готовая часть пачки сохраняются.

Почему сейчас:
Понятное исправление ошибки на выбранном языке — обязательная часть рабочего пути. Отложенный перевод заставляет казахоязычного пользователя разбираться с русским сообщением в момент сбоя.

Не входит:
Разные языковые видео, новая модель video progress, машинный перевод профессиональных программ, captions/transcoding и миграция исторических материалов.
Отдельные RU/KZ файлы — не доказанный дефект согласованного минимума: один materialId допускает общий двуязычный PDF/ролик. При подтверждённом наличии разных PDF полезно добавить отдельные ссылки следующим этапом с backward compatibility. Два разных видео требуют явной стратегии прогресса по asset/revision; нельзя переносить просмотр между несовпадающими таймлайнами. Эта функция пока отложена.

Переиспользование:
common.tsx mapper, current language state, existing error codes, batch selection/autosave.
Данные: бизнес-миграция не нужна; API сохраняет message для старого UI, добавляет code/params.
Откат: старый клиент продолжает понимать message; известный пробел перевода остаётся явно отмеченным, факты обучения не меняются.

Объём S–M, риск низкий, уверенность высокая.
Приёмка: KZ expired access, ошибка employer row, ошибка документа, один invite/recovery отказ; после повтора готовые строки и выбранные значения сохраняются. Полный повтор browser suite не требуется.
UX: +0 обязательных действий и +0 повторного ввода. Язык сообщения выбирается существующей настройкой.

F4. Полнота событий аудита

Источник:
§13 ¶345–353, §39 ¶860–885, §75.22; L10.
Состояние частично; неполнота обязательной детализации Audit Log.
Код: core.ts:7/130; schema.prisma:726; auth.ts:218; courses.ts:148/158/166.

Что есть:
Append-only AuditEvent, actor/time/action/entity/correlation, scope, защищённый просмотр. Журнал не отсутствует.

Минимальный остаток:
Доверенный источник IP и его provenance по принятой proxy policy; минимальный before/after diff значимых изменений draft content/profile/прав. Достаточно данных для понимания изменения, без паролей, token, полного закрытого файла и избыточных ПДн. Для worker — явный service actor/source, не фиктивный IP браузера.

Почему сейчас:
При увеличении числа редакторов и курсов одной revision мало для расследования. До расширения ролей зафиксировать, кто и что изменил.

Не входит:
SIEM, универсальный event sourcing, медицинские payload в логах, попытка восстановить неизвестные исторические значения.
Переиспользование:
Context/audit/AuditEvent, append-only trigger, /audit, correlationId.
Данные: optional new metadata/column для новых событий. Старые записи остаются unknown, не заполняются догадкой.
Зависимость: согласовать доверенную proxy policy с S1.
Откат: прекращение записи новых optional полей не удаляет прежние события; append-only остаётся.

Объём M, риск средний из-за privacy, уверенность высокая.
Приёмка: один вход через доверенный proxy, одна правка курса/profile и одна смена права; есть безопасный diff/IP provenance; spoofed XFF прямого клиента не доверяется; чужой tenant не читает audit; секретов нет. Ретест всех исторических событий не нужен.
UX:0 действий,0 повторных полей; подробность в audit для ответственной роли.

Вопросы остаются single/multiple. Поиск существующего вопроса переносит готовые тексты/переводы/options, не создаёт повторный ручной ввод.
Публикация фиксирует конкретную редакцию и прежний snapshot. Изменение библиотеки не обновляет активные CourseVersion/ExamAttempt.
Старые embedded вопросы продолжают читаться без массовой нормализации. Перенос в библиотеку — явное действие методиста с provenance; не объединять по одинаковому prompt.
Прежняя случайная выборка переиспользуется; распределение квот по темам и универсальная сложность экзамена не входят.

Почему сейчас:
При расширении числа программ копирование вопросов быстро разойдётся по текстам/переводам и исправлениям. Источник и редакция нужны до массового наполнения. Это меньше риска, чем сразу новые types/ручная оценка.

Переиспользование:
lmsQuestionSchema, CourseEditor, published snapshot, server grading/selection, tenant guards.
Данные: аддитивные Question/QuestionRevision либо эквивалентная минимальная библиотека + nullable reference в content, без обязательного превращения всех JSON в relational tables.
Backward compatibility: сохранённый snapshot остаётся достаточным для чтения/оценки без обращения к текущей библиотеке.
Rollback: отключить новый выбор из библиотеки, сохранённые данные/версии не удалять; опубликованный snapshot работает как раньше.

Зависимости: F2, F4. Профессиональную правильность нового вопроса и перевод подтверждает методист; инженерная проверка использует synthetic.
Объём M, риск средний, уверенность высокая.
Не входит: import5000 из произвольного файла, AI-вопросы, новые types, отдельная большая аналитика вопросов, автоматическое обновление всех курсов.

Приёмка:
Один вопрос используют два курса; в библиотеке новая редакция; старый курс/попытка сохраняет прежнюю; новый draft явно выбирает новую; чужой tenant не видит банк; grading прежнего single/multiple не изменён. Один пользовательский путь поиска/вставки достаточно вместе с этой version-boundary проверкой.
UX: подготовленный поиск/выбор заменяет ввод всех известных полей; первичное авторство/проверка неизвестного содержания отдельно. Обычному оператору +0 экранов и действий.

4. Минимальные меры масштабирования

S1. Ограничить конкретные дорогие операции

Источник:
§1 ¶41–43, §51–53, §73; согласованный TZ §10/UX05.
Принадлежность: безопасность/работоспособность текущих функций плюс новые инженерные рекомендации.
Отдельные дефекты каталога и >64MiB UX относятся к существующему MVP; мощность тысяч пользователей пока не доказана.

Фактическая база:
Сохранённый burst100/400 запросов, p95≈799ms,0 неожиданных5xx, длительность≈2.9s и1 курс. 250 assignments отдельно. Новую нагрузку сейчас не запускали.

Граница первой проходки:
1) Session/user-aware бюджеты authenticated чтения/autosave; отдельный login budget и доверенный proxy source. RateLimit по общему req.ip600/min не должен блокировать разных обычных слушателей за одним proxy.
2) Правильный catalogue published filter/count до paging; batch latest versions/profiles. Stable ordering с tie-breaker.
3) Ограниченные projections/results: не загружать все enrollment IDs до страницы, batch events/links/artifacts вместо per-row queries. Только реально отображаемые list fields; полный content — в detail.
4) Массовое назначение автоматически дробится на ограниченные транзакции с дедупликацией/возобновлением/сводкой строк. Сохранить один пользовательский запуск; 250 — масштаб прошлой проверки, не бизнес-потолок. Не принимать10000 как доказанное допустимое выполнение в одном tx30s.
5) Private video Range не пересчитывает hash всего immutable blob на каждом запросе. Кеш проверки должен зависеть от проверяемой identity/version и инвалидироваться при изменении; сохранить контроль подмены и periodic integrity check.
6) Материалы получают budget параллельных крупных uploads/временного диска и cleanup. Защита сессии/tenant/типов/путей остаётся.
7) Bundle >64MiB не требует ручного деления. Переиспользовать существующий splitter/queue/storage с сохранением manifest и selection; bounded generation/stream, не большой Buffer всех частей в API.
8) Зафиксировать суммарный бюджет соединений API/render/integration относительно PostgreSQL до добавления replicas. Новые индексы — только по плану изменённой выборки; не создавать их наугад.

Переиспользование и точные точки:
auth.ts:51/79/182; app/api/[...path]/route.ts:28–40; main.ts.
courses.ts:41–74; document-bridge.ts:624–665/:726–767.
validation.ts:25; enrollments.ts:160–237; core.ts:151–154.
materials.ts:197–215; auth.ts:143–156.
printing/src/index.ts:19–35; render-worker queue.ts; existing unique enrollment constraints.

Почему сейчас:
Эти ограничения видны в коде, не требуют гадать о production. Если сначала увеличить число пользователей/файлов, общий limiter, tx timeouts и дисковое чтение ухудшат обычный путь. Ни одно из них не требует микросервисов.

Не входит:
Новый брокер, Redis/PgBouncer по умолчанию, межtenant scheduler, CDN/transcoding, тысячи новых соединений, большая нагрузочная программа, полная оптимизация всех старых DEMO endpoints.
Fairness: существующий FIFO/leases работают; общую межцентровую fairness выбрать позже по наблюдению. Индивидуальный лимит обучения/документов не вводить ради тестовой цифры.

Данные/откат:
Старые version/result/issuance не менять. Batch operation metadata при необходимости аддитивны; ключ дедупликации не меняет прежнюю уникальность. Новые индексы обратимы без потери бизнес-данных. Кеш целостности не источник истины; rollback возвращает строгую проверку с меньшей производительностью. Лимиты откатываются в согласованный безопасный профиль, не в неограниченный доступ.
Объём M–L (разные resource boundaries), риск средний, уверенность высокая в механизмах, средняя в объёме batch/archive. Это крупнейший пакет, поэтому строго исключить общий performance rewrite.

Будущая узкая приёмка:
- несколько страниц каталога/результатов без пропусков/дубликатов/черновиков в total;
- измеренный bounded query count для одной страницы, EXPLAIN только изменённого запроса;
- две сессии за одним proxy сохраняют ответы независимо, поддельный proxy-header не доверяется;
- один batch через границу chunk и повтор после частичного выполнения, без дублей/потери успешных строк;
- несколько Range одного файла не читают весь blob заново, изменение bytes обнаруживается;
- одна перегрузка upload admission и один oversized bundle с автоматическими частями, правильным scope и inventory.

Это не load test на тысячи. После выбора production environment отдельный короткий mixed-workload acceptance profile должен включить реальную продолжительность, доли video/read/autosave/exam finish/bulk/render, file sizes и DB/storage/CPU metrics. До него точную ёмкость не заявлять.

UX:
0 новых обязательных действий. Размер внутренних chunks/lease/pool скрыт от оператора. Повтор сохраняет состав/готовые строки, не просит «выберите меньшую часть». Реальные подписи и согласования сохраняются.

S2. Поставка и видимость фоновой обработки

Источник:
Согласованный TZ §8/10, SAN02/SAN05/SAN11; полное §51/73.
Тип: эксплуатационное состояние/неполнота поставки, не отсутствие реализованного worker.

Что есть:
integration-worker выполняет expiry/preparation/internal transitions, NOT_CONNECTED не означает отключение его локальной пользы. dev.mjs запускает4 процесса; render queue имеет heartbeat/leases/fencing; sanitary recovery проверен раньше.
Последний snapshot integration STOPPED после автоматического отказа «blocked by policy». В исследовании перезапуск не выполнялся.

Минимальная граница:
- Явный integration service/child и supervision в действительно поддерживаемых локальных/release profiles.
- Manifest/copy/install соответствуют autonomous workspace.
- Отдельный heartbeat, возраст ожидающих заданий, безопасная ошибка и деградация именно integration, независимо от renderer.
- Ingress пропускает новые разрешённые LMS/learn/sanitary pages и API в рамках product-policy. Сохранить deny-by-default, не заменить allowlist на «пропустить всё».
- Upload budget на material routes соответствует принятому профилю, не глобальное снятие12MiB для всех endpoints.
- Offline backup/restore checklist учитывает обоих workers и реальную остановку writers. Restore engine переиспользуется.
- Worker health не требует открывать страницу оператору; техподробности находятся у администратора эксплуатации.

Точки:
deployment/compose.yaml:80–83, railway/start.mjs:176–190, Dockerfile:11–18, nginx.conf:13/32–37 и nginx-tls.conf:14.
apps/integration-worker/src/main.ts:15–34; api/controller.ts:76–97.
deployment/backup.mjs:173–224/273–313; docs/OPERATIONS_RU.md:81.

Почему сейчас:
Без worker не выполняются фоновые завершения истёкших попыток и автоматическая подготовка документов/санитарных записей, а health renderer может показывать готовность. Серверный deadlineAt и ограничения времени при чтении/отправке попытки сохраняются. Нельзя масштабировать стенд, в котором один из обязательных фоновых процессов не входит в поставку.

Не входит:
Production запуск/миграция/deploy, реальная внешняя доставка, попытка обойти прежний policy rejection, изменение power settings или соседних процессов. Подготовка runtime profile и его будущая локальная проверка требуют отдельного реализационного поручения после этого исследования.

Данные/совместимость/откат:
Схема heartbeat может расширяться аддитивно; durable outbox/lease семантика сохраняется. При rollback остановить только принадлежащий внедрению worker по плану, сохранить PENDING; не удалять очередь и не отмечать её DONE. Не смешивать render queue и external delivery.
Объём M, риск средний, уверенность высокая по source inconsistency; container build failure не воспроизводился.

Будущая узкая приёмка:
Один disposable локальный lifecycle smoke для выбранного supported profile: start → один PENDING → stop integration → health degraded → resume → DONE один раз. Renderer не маскирует остановку. Один проход /lms через ingress и material upload через тот же ingress. Source validation для остальных profiles; их готовность не объявлять по одному проверенному.
Для backup только проверить обновлённый writer checklist/совместимость нового payload; полный исторический restore suite повторять лишь при изменении механизма хранения.
UX:+0 действий. Очередь не превращается в кнопку ручного продвижения каждого статуса.

6. Условие завершения проходки

Проходка может быть принята, когда все восемь выбранных пакетов выполнены в своей минимальной границе и выполнены только относящиеся к ним условия:

1. Один серверный точный допуск, отсутствие невидимых зависимостей и неисправимых черновиков.
2. Достоверные immutable question revisions; прошлые attempts/results/documents/номера неизменны.
3. Новые ошибки корректны RU/KZ; работа существующих общих материалов не изменена. Отдельные языковые assets не являются условием окончания этой проходки.
4. Новые значимые события имеют безопасное доказательство изменения/источника; старые неизвестные данные не выдуманы.
5. Основные list/count/export согласованы, scope сохраняется; большой batch/bundle не требует ручного дробления.
6. Отдельные обычные сессии за proxy не блокируют друг друга; file/DB/queue ресурсы имеют понятную границу.
7. Выбранный локальный deployment profile включает integration и показывает его реальное состояние; один recovery smoke без дублей подтверждён.
8. A1 и A2 закончены как реальные UI→API→данные→результат пути, а не таблица/endpoint/макет.
9. Подготовленные прежние действия DEMO сохраняют бюджет: назначение≤2, комплект≤2, готовое скачивание≤2, продолжение1, автоматический sanitary transition0; ноль повторного ввода известных бизнес-данных. Вход, первый ввод, решение директора, подписи и новый перевод считаются отдельно.
10. LOCAL/PROVIDER_SANDBOX/PRODUCTION/LMK статусы раздельны; внешние блокеры не объявлены PASS.

Достаточность проверки при будущей реализации:
Один адресный набор инвариантов F1/F2/A2, выбранные отрицательные RU/KZ/scope cases, один короткий UI путь A1, один resource-boundary набор S1 и один lifecycle smoke S2. Не повторять полный browser/render/load набор многократно без конкретного изменения/провала.
