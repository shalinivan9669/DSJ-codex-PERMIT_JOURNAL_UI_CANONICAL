# Тест NCALayer на Railway и Vercel

Этот режим позволяет пройти подписание и выпуск в отдельном тестовом центре на размещённом сайте. Пользователь выбирает свой ключ в NCALayer на своём компьютере; Railway получает CMS и сохраняет её как тестовую. Сервер не проверяет криптографическую корректность CMS, соответствие подписи PDF, личность, доверие НУЦ и отзыв сертификата. eGov этим режимом не включается.

Инструкция описывает подготовленные настройки, а не выполненный деплой. Базовая схема сервиса, тома и БД — в [Railway README](README.md), frontend — в [Vercel guide](../VERCEL_FRONTEND.md). Не переносите локальную БД, учётные записи, артефакты, файлы ключей или пароли NCALayer в облако для этого прогона. Тестовый центр создаётся заново штатной командой.

## 1. Подготовить окружение и отдельный центр

Выберите конкретные Railway project/environment/backend service и соответствующий Vercel frontend. Обновите **оба сервиса одним и тем же commit** с поддержкой hosted mock: старый frontend может не показывать предупреждение о тестовом режиме и пакетную кнопку. API, render worker и integration worker запускаются существующим supervisor; закрытое хранилище остаётся на `/data/artifacts`. Backend сохраняет `NODE_ENV=production` и `HOST=0.0.0.0`. NCALayer на сервер устанавливать не нужно: браузер пользователя соединяется с `wss://127.0.0.1:13579/` на его компьютере.

До включения мока оставьте `DEMO_HOSTED_SIGNATURE_MOCK=0` и `DEMO_LOCAL_SIGNATURE_MOCK=0`. Для однократного создания центра задайте в Variables выбранного backend service:

| Переменная            | Значение                                                                  |
| --------------------- | ------------------------------------------------------------------------- |
| `DEMO_ADMIN_EMAIL`    | Новый уникальный адрес тестового директора, не адрес существующего центра |
| `DEMO_ADMIN_PASSWORD` | Отдельный приватный пароль длиной от 12 символов                          |
| `DEMO_TENANT_NAME`    | Явное название, например `Тест NCALayer — Railway`                        |
| `DEMO_SAMPLE_DATA`    | `1` только для этого создания тестового центра                            |

Переменные Railway применяются к процессу после просмотра и развёртывания staged changes. Не добавляйте секреты с префиксом `NEXT_PUBLIC_`. [Railway Variables](https://docs.railway.com/variables).

После запуска контейнера с нужной БД и смонтированным `/data` подключитесь к нему. Замените идентификаторы на выбранные значения:

```sh
railway ssh --project "<PROJECT_ID>" --environment "<ENVIRONMENT_ID>" --service "<BACKEND_SERVICE_ID>"
```

Внутри контейнера выполните:

```sh
cd /app
node deployment/railway/start.mjs -- pnpm run setup
```

Это существующий `scripts/setup.ts`, а не новый seed: он создаёт директора и `demoOnly=true` центр, устанавливает шаблоны и синтетический подтверждённый профиль. Новый центр получает тестовые подтверждения шаблонов; привязки ЭЦП, заявки и подписи команда не создаёт. В результате выводится `tenantId`; сохраните именно его для настройки следующего шага. Повтор с тем же email не меняет пароль, а попытка применить `sample=1` к обычному центру завершается ошибкой — используйте новый адрес, не меняйте флаг существующего центра вручную.

`railway ssh` выполняет команды в удалённом контейнере. `railway run` выполняет их локально и не подходит для установки шаблонов в Railway volume. Pre-deploy тоже не подходит: его отдельный контейнер не имеет этого тома. [Railway SSH](https://docs.railway.com/cli/ssh), [Railway run](https://docs.railway.com/cli/run), [Pre-deploy](https://docs.railway.com/deployments/pre-deploy-command).

После создания удалите однократные `DEMO_ADMIN_EMAIL`, `DEMO_ADMIN_PASSWORD`, `DEMO_TENANT_NAME` и верните `DEMO_SAMPLE_DATA=0`. Это не удаляет центр и не меняет его тестовый статус. Проверьте вход через выбранный frontend: `GET /api/context` должен показывать полученный `tenant.id` и `tenant.demoOnly=true`.

## 2. Включить hosted mock только для этого центра

В Variables того же Railway backend задайте:

| Переменная                             | Значение                                                                                            |
| -------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `NODE_ENV`                             | `production`, как в Docker image                                                                    |
| `DEMO_LOCAL_SIGNATURE_MOCK`            | `0`; локальные ограничения остаются отдельными                                                      |
| `DEMO_HOSTED_SIGNATURE_MOCK`           | `1`                                                                                                 |
| `DEMO_HOSTED_SIGNATURE_MOCK_TENANT_ID` | Один UUID `tenantId`, выведенный `setup`; без списка или `*`                                        |
| `DEMO_ORIGIN`                          | Канонический публичный HTTPS origin выбранного Vercel frontend                                      |
| `DEMO_API_ORIGIN`                      | Публичный HTTPS origin Railway API, а не адрес БД, не `*.railway.internal` и не URL frontend-прокси |

Оба origin должны быть без завершающего `/`, пути, credentials, query и fragment; localhost и частные адреса не подходят. Значение `DEMO_ORIGIN` совпадает с frontend. `DEMO_API_ORIGIN` на backend для hosted mock обязательно; соответствующее значение на Vercel также участвует в сборке proxy, поэтому изменение frontend upstream требует новой сборки по Vercel guide.

Просмотрите изменения и разверните выбранный backend. Мок доступен только когда одновременно совпали явный флаг, один разрешённый tenant UUID, активный `demoOnly` центр и заявка `demoMode=true`. Допустимые значения `NODE_ENV` для этого режима — `production` и `test`; `development` не включает hosted mock. Привязки к специальной Railway-переменной нет: ограничения проверяет API.

Обычные центры и другие тестовые центры не получают мок даже при включённом флаге. Их существующие настройки настоящего проверяющего сервиса сохраняются; не очищайте ради теста `DEMO_SIGNATURE_VERIFIER_URL` и `DEMO_SIGNATURE_VERIFIER_TOKEN`, если они уже используются. В разрешённом тестовом центре внешний проверяющий сервис для мокового прогона не требуется.

## 3. Подготовить роли до оформления заявки

Войдите тестовым директором и откройте `/settings?tab=signatories`. `setup` не создаёт `SignatoryBinding`. Для проверки одного аккаунта в трёх ролях явно сохраните три назначения на этого тестового пользователя: **Директор**, **Председатель комиссии**, **Преподаватель**. Это три полномочия, а не три новых аккаунта. В демонстрационном центре можно использовать одно явно синтетическое ФИО, например `Тестовый Директор`, и одинаковый тестовый ИИН из 12 цифр во всех трёх назначениях. При hosted mock фильтр ИИН/БИН в NCALayer не отправляется, а личность владельца ключа не утверждается.

Паспортные данные владельца ключа для этой настройки не нужны. Локальный сценарий `scripts/verification/prepare-director-print-local.ts` в облаке не запускается: его локальные учётные записи, назначения и данные не переносятся автоматически.

В реквизитах центра согласуйте это же ФИО руководителя, председателя (первая строка комиссии) и преподавателя в списке сотрудников. Имена используются для однозначного выбора назначений. Остальной состав и обязательные реквизиты формы заполните тестовыми значениями, подтвердите профиль. В `/settings?tab=templates` проверьте нужные версии. Если форма требует других членов комиссии, назначьте их явно: пакетная кнопка подписывает только собственные действующие роли аккаунта.

Создайте **новую** тестовую заявку после этих назначений: например, организация с двумя-тремя синтетическими работниками и отдельная заявка физлица. В `demoOnly` центре сервер принудительно сохраняет `demoMode=true`. Проверьте, согласуйте и сформируйте документы штатным путём. Настройки не переписывают подписантов ранее оформленного выпуска; для старого выпуска с недостающими ролями требуется штатное исправление/новое оформление.

В кабинете директора должна появиться доступная кнопка «Подписать весь комплект через NCALayer» и явная отметка тестового режима. NCALayer получает массив PDF одним запросом. Полученные CMS сохраняются отдельно для каждой пары PDF/роль. Чужие, уже подписанные и оформленные на бумаге документы не включаются. При сетевом сбое после получения CMS используйте «Повторить сохранение подписей» на той же странице: повторный выбор ключа не требуется. Закрытие страницы теряет ещё не отправленные CMS из памяти браузера.

## 4. Проверить результат и выключение

Прогон считается проверенным только после выполнения на выбранном сайте:

- Отметка тестового режима видна в подписании и на листе сведений об ЭЦП. ФИО читается из сертификата CMS с указанием, что личность не проверена; время — получение сервером.
- PDF/DOCX для печати содержат отметки и отдельный лист с QR. QR открывает авторизованную страницу `/signature-evidence/:artifactId` на HTTPS frontend. Оригинал PDF остаётся доступен отдельно и сохраняет исходный SHA-256.
- ZIP содержит неизменённые оригиналы, `.p7s` и отдельные `print-copies/`. Тестовая запись использует `NCALAYER_HOSTED_TEST`, `HOSTED_TEST_MOCK`, `valid=false`; manifest не выдаёт мок за проверенную ЭЦП.
- После обязательных тестовых подписей выпуск проходит обычный переход к выдаче. Другой аккаунт не может подписать чужую роль; обычный и неразрешённый тестовый центры не получают hosted mock. Публичная проверка тестового выпуска недоступна.
- После `DEMO_HOSTED_SIGNATURE_MOCK=0` и применения изменений повтор мокового подписания и экспорт тестового подписанного комплекта отклоняются. То же происходит при удалении разрешённого tenant UUID. Исходные PDF без добавленных отметок не переписываются.

Для завершения теста оставьте флаг `0` и очистите `DEMO_HOSTED_SIGNATURE_MOCK_TENANT_ID`, применив staged changes. Сохранённые тестовые подписи не превращаются в официальные: для настоящих документов нужен обычный центр и сервер проверки по [контракту ЭЦП](../../docs/SIGNING_CONNECTION_RU.md).

В свидетельстве прогона укажите commit, Railway/Vercel deployment IDs, тестовый tenant UUID, число документов/ролей и фактические результаты. Ключи, пароли и полные CMS в отчёт не помещаются.
