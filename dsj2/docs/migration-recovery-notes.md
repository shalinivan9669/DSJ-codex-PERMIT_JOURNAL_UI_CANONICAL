Состояние на 4 ноября 2026 года. Это анализ, а не инструкция к развёртыванию: безопасная миграция для рабочего контура пока не подготовлена и не проверена.

## Что обнаружено

- На пустой PostgreSQL текущий `prisma migrate deploy` прерывается на `202604100430_p0_compliance_bridge`: внешний ключ ссылается на отсутствующую таблицу `Organization`.
- Сравнение имён моделей и перечислений из `packages/database/prisma/schema.prisma` с командами `CREATE TABLE` и `CREATE TYPE ... AS ENUM` во всех существующих миграциях показывает 31 модель и 29 перечислений, для которых в этой цепочке нет создания. В частности, отсутствуют `Organization`, `Position`, `DocumentEnvelope`, `BriefingJournal` и перечисление `DocumentKind`. Счётчик основан на статическом поиске и сам по себе не является доказательством полного совпадения остальных объектов.
- В доступной истории Git не найдена миграция с `CREATE TABLE "Organization"`. Отсутствующие миграции могли находиться вне этого репозитория; их содержимое и состояние внешних установок неизвестны.
- Предыдущие миграции содержат переносы и создание связанных записей для существующих организаций. Для действующей базы их нельзя без проверки заменять созданием одной только схемы.
- Например, `202604120910_briefing_journal_entry_hardening` создаёт журналы, политику хранения и типы документов выборкой по уже существующим организациям. На пустой базе такие выборки не добавят ни одной записи. Необходимо отдельно проверить, как эти данные появляются при последующем создании организации; не следует считать их автоматически созданными только потому, что базовая схема успешно установлена.
- Миграция `202606061600_work_permit_mvp` содержит ограничения `BrigadeMember_subject_check` и `PpeIssueRecord_subject_check`, требующие ровно одного из сотрудника или работника подрядчика. Они заданы SQL, а не моделью Prisma. Одно только построение схемы из `schema.prisma` их не восстанавливает.

Генерация SQL из текущей Prisma-схемы в режиме сравнения с пустой схемой выполняется, но полученный SQL не является проверенной заменой всей истории миграций. Нельзя считать проблему решённой командой `db push` или массовой отметкой исторических миграций как применённых.

Создана отдельная пустая PostgreSQL-база с тестовым именем. После построения схемы из Prisma получено 75 таблиц, но оба названных SQL-ограничения отсутствовали. Временное добавление обоих ограничений успешно; проверена их видимость в `pg_constraint`, а ограничение `PpeIssueRecord_subject_check` отклонило тестовую запись без сотрудника и работника подрядчика. После этого `prisma migrate diff` по-прежнему не показал различий с моделью: следовательно, этот diff не подтверждает наличие таких ограничений. Временная база удалена; существующая база и её история миграций не изменялись.

Статическая сверка всех 25 доступных миграций с SQL, сгенерированным из текущей модели, выявила:

- В доступных миграциях не найдены создаваемые функции, процедуры, триггеры, представления, расширения, политики и дополнительные `CHECK`/`EXCLUDE`. Это не доказывает отсутствия объектов из потерянных миграций или внешних источников.

Дополненный экспериментальный SQL успешно применился к отдельной новой временной базе. Оба `CHECK` отклонили тестовые записи без участника. Из семи исторических `INSERT` на пустой базе шесть выполнились без добавления данных; перенос записей журнала завершился ошибкой `42804`: поле `employeeStatus` имеет тип `BriefingParticipantStatus`, а выражение — `EmployeeInstructionStatus`. Поэтому перенос истории ещё нужно восстановить и проверить на синтетических данных; простое повторное выполнение SQL не подходит.

Сверялись только системные каталоги локальной базы без чтения рабочих строк. В них отсутствуют оба исторических `CHECK`, четыре указанных внешних ключа и три индекса; остальные сопоставленные по имени индексы и ограничения не отличались. Это наблюдение не подтверждает состояние других установок. После дополнения экспериментальной базы `prisma migrate diff` предложил удалить четыре внешних ключа и три индекса, поскольку их нет в текущей Prisma-модели. До любого применения нужно согласовать модель и SQL-ограничения так, чтобы будущие миграции не удаляли их автоматически. Все временные базы эксперимента удалены; действующие данные, миграции и настройки развёртывания не менялись.

## Синтетическая проверка переноса и начальных данных

На новой временной базе с экспериментальной схемой проверены вымышленные записи без доступа к рабочим данным. Все пять значений исходного `EmployeeInstructionStatus` присутствуют в целевом `BriefingParticipantStatus`; преобразование через текст в отдельной экспериментальной копии SQL сохранило все пять значений. Повторный запуск на тех же записях не создал дублей. Это не доказывает корректность полного переноса подписей, архивов и записей реальных установок.

Обнаружены ещё два важных случая, которые необходимо обрабатывать явно до переноса:

- В исходной проверке совпадения регистрационных номеров два `NULL` считаются одинаковыми. Если ранее перенесена запись без номера, вновь обнаруженная запись той же организации без номера пропускается. Экспериментальная проверка совпадения номера только при значении, отличном от `NULL`, перенесла вторую запись; повторный запуск сохранил общее число записей. Правило сопоставления требует более широкой проверки, в том числе для пустой строки, повторных номеров и уже существующих записей.
- Организация может одновременно совпадать по `id` с одной строкой и по `legacyCompanyId` с другой. Исходное соединение `OR` тогда возвращает две строки для одной старой записи и перенос завершается нарушением уникальности её `id`. В синтетическом примере это подтверждено ошибкой `23505`. Нужно заранее находить и разбирать такие неоднозначности; автоматический выбор организации здесь небезопасен.

По коду создание компании создаёт `Company` и ответственного пользователя, но не все записи исторического backfill. При работе с инструктажем `briefing-records.service.ts` создаёт нужный журнал через `ensureJournal`; типы инструктажей создаются при построении карточки сотрудника в `employee-compliance.service.ts`; базовая политика хранения разрешается и при необходимости создаётся через `ensureRetentionPolicyResolved` в `core-platform.service.ts`. Это отложенное создание для конкретных путей, а не доказательство, что все необходимые записи появляются сразу или что все пользовательские сценарии новой организации проверены.

Скрипты синтетического эксперимента и результат находятся в указанной временной папке как `synthetic-status.ps1`, `synthetic-status.cjs` и `synthetic-status-results.json`; временная база после проверки удалена. Исправления исследовательские, в миграции и рабочую базу не внесены.

Для проверки совместимости с Prisma подготовлена отдельная экспериментальная копия модели `schema.aligned.prisma`: в ней описаны четыре найденных исторических внешних ключа и три индекса. `prisma validate` прошёл, а сравнение с экспериментальной базой вернуло пустую миграцию вместо предложенного удаления этих семи объектов. Это полезно для дальнейшей подготовки схемы, но не является доказательством совместимости с данными и настройками существующих установок. Проверенные ранее `CHECK` и порядок enum штатное сравнение Prisma не подтверждает; их нужно проверять отдельно. Исходная схема проекта не менялась.

## Что нужно для безопасного решения

1. Найти исходные отсутствующие миграции или восстановить согласованное состояние схемы и SQL-ограничений. Исторические миграции в репозитории не переписывать.
2. Отдельно подготовить и проверить базовую схему **только для новой пустой базы**: модели, индексы, внешние ключи и все SQL-ограничения; проверить также начальные данные, создаваемые миграциями, и будущие миграции после базовой версии.
3. Для существующих установок сравнить реальные схемы и историю миграций на копиях без персональных данных, определить различия и отдельную стратегию совместимого обновления и отката. Не считать их одинаковыми с новой пустой базой.
4. Проверить создание с нуля, последующее обновление, восстановление из резервной копии и приложение на отдельных тестовых базах. Реальные данные и существующую историю без отдельного плана не менять.

Для нового контура возможный вариант — отдельная версия базовой миграции с SQL, выведенным из утверждённой схемы, с явно добавленными проверенными SQL-ограничениями и отдельно учтёнными начальными данными. До принятия варианта нужно сверить SQL всех исторических миграций, а не только названные два `CHECK`. Должны проходить проверки отсутствия и наличия каждого участника, внешних ключей, индексов, начальных данных, реального запуска приложения и применения следующей миграции поверх новой базы. Перенос старых записей в действующих контурах — отдельная задача; его нельзя подменять пометкой миграций как выполненных.

Работы затрагивают изоляцию организаций, данные пользователей и контур подписей. Применение новой схемы и изменение процесса развёртывания требуют явного разрешения согласно `AGENTS.md`; сама задача не зависит от формы протокола, которую согласует заказчик.
