# Удобный повседневный ввод: один человек, небольшой заказ и список

## 0. Простой случай не усложняется ради массового

Один человек оформляется в компактном пути с выбранными документами и только необходимыми им полями. Найденная запись используется повторно. Несколько документов не требуют повторных ФИО и общих реквизитов. Для нескольких людей появляются общие значения и исключения; большой список использует ту же модель и массовые действия.

Не требовать отдельного создания заказа/группы/компании через мастера, если текущая задача этого не требует. Не убирать реально необходимые сведения об основании, работодателе и результатах. Внутреннюю связь с событием система может создать без отдельной ручной анкеты при наличии необходимых фактов.

G1/G2 ниже — нагрузочная часть приёмки; V01–V12 обязательны наравне с ней.

## 1. Экран заявки

Сохранить существующий рабочий интерфейс, но поставить общий контекст выше индивидуальных карточек. В верхней компактной области — релевантные выбранному процессу заказчик/работодатель, набор, программа/событие, даты, основание, комиссия и режим протокола. Нерелевантные поля не показывать как обязательные. Ниже — список людей с назначениями и исключениями. Справа — детали только выбранной строки. Общие реквизиты не размножаются в 100 раскрытых формах.

Показывать счётчики по фактическому составу без технического шума. Например, в G1: «100 человек · 100 назначений · 1 протокол · 101 документ»; в одиночной заявке не навязывать все групповые счётчики. Отдельно показывать готовые файлы по форматам. До регистрации номер выглядит «Будет присвоен при оформлении»; прогноз номера не является резервом.

## 2. Иерархия и происхождение

Центр/профиль и комиссия задаются версионированной настройкой. Паспорт услуги предлагает проверенный набор и допустимые значения. Заявка задаёт общий заказный контекст. Событие задаёт фактические даты, программу, категорию, комиссию и основание. Участник задаёт ФИО, должность, фото там, где требуется, индивидуальный результат и разрешённые исключения.

Приоритет: допустимое индивидуальное значение → событие → заявка → выбранный пресет → версия центра. Это разрешение только для полей, которым данный уровень подходит. Для ФИО нет fallback из компании; номер не вводится через пресет; результат не наследуется как успешный. Одинаковое обязательное поле общего протокола не может отличаться между участниками: требуется другое событие/версия, а не скрытый override.

У значения есть происхождение: наследовано, введено вручную, импортировано, вычислено по подтверждённой политике. Ввод того же текста вручную всё равно создаёт ручное происхождение. Нельзя определять ручной статус только сравнением текста с прошлым default: это уже частично решено `biotManualFields`, расширить последовательно.

Пустой override, сброс к наследованию и отсутствие исходных сведений — разные операции. «Очистить» не должно незаметно подставить старое общее значение. Для общих значений, выбранных до импорта, позднее добавленные строки получают актуальное наследование. Для выданных документов разрешение выполнено и сохранено в snapshot навсегда.

## 3. Массовая операция

Оператор выбирает область: все строки, явно выбранные, выбранное направление, событие или только строки с конкретной ошибкой. Фильтр не равен выбору: интерфейс явно показывает, какие скрытые строки включены. Операция содержит field mask, режим и ожидаемую revision.

Режимы: заполнить только пустые; обновить наследуемые; заменить выбранные поля с явным подтверждением. Перед применением — число затрагиваемых людей/назначений и компактный diff, особенно если есть ручные исключения. Не выбирать молча «все документы всех направлений» как текущий BulkDialog.

Общие поля: дата документа, фактические даты обучения/проверки, программа, часы по применимому паспорту, категория, отрасль, основание, комиссия/профиль, работодатель и подразделение, язык/формат выдачи. Не все поля универсальны для всех форм: несовместимые назначения объясняются и не меняются.

Добавление набора идемпотентно по его семантике: форма + событие + роль документа, а не только templateId. Повтор одного набора не создаёт копии. Новый фактический курс того же типа допустим как отдельное назначение. Оператор может убрать документ только из чернового плана с показом влияния на протокол и комплект.

Результаты принимаются отдельной командой: загрузить подтверждённую ведомость или применить известный результат к выбранным участникам конкретного события, указав источник/ответственного. Нет заранее включённого «все сдали». Для разных направлений даже у одного человека результаты независимы.

## 4. G1 — 100 человек, одно направление

Синтетический центр уже настроен и явно маркирует документы. Оператор создаёт заявку компании, вставляет/импортирует `fixtures/100_people.*`, назначает всем PB-набор, выбирает одно событие PB-G1 и одну комиссию. Общие поля задаются один раз. Положительные тестовые результаты поступают из отдельной синтетической ведомости; в продукте они не создаются самостоятельно.

Проверка данных объединяет общие ошибки: отсутствие председателя показывается одним сообщением «Комиссия события не заполнена: затрагивает 100 участников», а не 100 однотипными строками. Индивидуальные ошибки открывают нужную ячейку. Контрольный лист содержит 100 человек, не 100 страниц карточек.

Регистрация даёт **100 удостоверений PB + 1 групповой протокол PB = 101 IssuedDocument**, без фиктивного получателя. По одному DOCX/PDF на документ, один основной XLSX и один основной ZIP дают **204 канонических задания и артефакта при стандартном выпуске всех четырёх форматов**. Черновые preview, контрольные листы, копии выдачи и новые экспорты считаются отдельно. Реализацию агрегированных файлов разрешено добавить, но нельзя подменять ими эти определения или доказательства.

В PB:PROTOCOL счётчик увеличивается на 1, в PB:CARD на 100. В каждой карточке — её человек и номер, общий номер протокола, правильная комиссия/даты. Протокол содержит 100 уникальных записей участников в согласованном порядке. Общие данные на уровне участника вводятся **0 раз**, индивидуальные панели в сценарии без исключений открываются **0 раз**.

## 5. G2 — 100 человек, 200 назначений, три протокола

Все 100 получают PB; первые 60 также PTM; последние 40 также БиОТ рабочих. Три совместимых события с отдельными программами/датами/правилами. Всего 200 индивидуальных положительных тестовых результатов, 200 удостоверений и 3 групповых протокола: **203 документа**, стандартно **408 канонических DOCX/PDF/XLSX/ZIP заданий и артефактов**. Для каждого направления общий контекст вводится один раз, а не 200 раз.

Проверить отдельные категории, периоды, комиссии и пределы применимости. Протокол ПТМ не получает данные БиОТ от общей кнопки. Новые формы групповых протоколов проверяются и версионируются; нельзя объявлять старый индивидуальный шаблон групповым только сменой enum.

## 6. Исключения

FAILED/ABSENT/UNKNOWN не дают положительного удостоверения. Система показывает план выдачи и не скрывает, что у людей различаются результаты. Протокол отражает допустимые фактические результаты по своей форме. Выборочная регистрация новых групповых единиц требует явной сводки; прежний атомарный individual-flow не менять незаметно.

Ручная особая дата/категория сохраняется при обновлении общих данных. Несовместимое с событием исключение предлагает разделение. Изменение компании/программы не меняет ФИО, результаты и прошлую историю. Одинаковые ФИО в строках 9 и 10 fixture — разные люди.

## 7. Клавиатура и восстановление

Сохранить AutosaveLane и expectedRevision; расширить payload всеми новыми связями. Перемещение между полями не посылает запрос defaults на каждую строку. Массовый patch должен быть одной логической ревизией, не 100 отдельных действий. Debounce не должен терять последние символы при preview/finalize.

Undo действует на черновой patch с проверкой текущей revision. При чужой правке не откатывать её молча: показать конфликт/обратный diff. Закрытый браузер до успешного сохранения не выдавать за гарантированный offline режим. При ошибке сети сообщение «Не сохранено» остаётся видимым; retry не размножает документы.

## 8. Скорость: что измерять

Обязательные количественные требования: 0 повторных вводов общих реквизитов на участниках; 0 ручных серверных номеров; 0 обязательных открытий индивидуальных панелей без исключений. После завершения mapping применение набора — одна команда, а не 100 команд.

Для тестовой среды зафиксировать CPU/RAM/браузер/БД/renderer и измерить p50/p95: редактирование ячейки, массовый patch, сохранение, validate, начало фоновой генерации, полный комплект. Цели интерактивности: обычный ввод без заметной блокировки, p95 реакции локального grid до 200 мс и локального применения массового изменения до 1 с на 100 строках. Это инженерные цели для согласованного стенда, не заявление измеренных результатов и не SLA массового PDF. Сетевое время и рендер считать отдельно; при превышении описать профиль и исправление, не фальсифицировать метрику.

## 9. Текущая дата и фото без лишних индивидуальных действий

Дата оформления новой заявки по умолчанию может быть «Сегодня» в часовом поясе центра; сервер фиксирует её при осмысленном действии и показывает фактическое значение. Оператор может выбрать иную календарную дату. Не считать «сегодня» доказательством дня обучения или проверки: фактические даты и результаты указываются отдельно. Уже оформленная дата никогда не плавает при повторном открытии.

Для форм, которым действительно нужно фото, добавить массовое сопоставление выбранных PNG/JPEG по устойчивому внешнему/табельному ключу с preview. Одна команда выбора нескольких файлов, отчёт matched/missing/ambiguous, подтверждение соответствия; не распознавание лица и не автоматическое присвоение по похожему ФИО. Существующие private PhotoAsset, ограничения пикселей/размера, нормализация и crop сохраняются. Повторное использование уже подтверждённого фото из карточки человека допускается с контролем актуальности и прав. Отдельная корректировка кадрирования открывается только для исключений. Бинарные данные не помещать в JSON draft. В тестах G1/G2 использовать существующий synthetic photo fixture через адаптер только для требующих фото форм.
