# Безопасность, миграции и эксплуатация

## 1. Не ослабить действующую границу

Автономный DEMO остаётся без `@dsj/*` runtime imports, старых JWT, DSJ БД и frozen workers. Новые возможности получают узкие разрешения в product-policy, page/proxy/API, server actions, jobs и downloads. Любой новый route вне allowlist закрыт до исполнения. Нельзя разрешить `/api/*`, универсальный `Public` или «SUPER_ADMIN видит всё» для обхода границы продукта.

Рабочая область — `dsj2/products/demo`. Если нужны изменения родительского шлюза/CI/AGENTS, они только про точную новую границу DEMO, без рефакторинга замороженной бизнес-логики. Прочитать все применимые инструкции и актуальные policy файлы; сверить их согласованность тестом.

## 2. Principal, tenant и customer scope

Tenant берётся из доверенной серверной сессии. Переданный в body/query tenantId — не источник прав. Для представителя работодателя нужна отдельная membership tenant+customer+role и при необходимости ограничение подразделений/людей. Center VIEWER не заменяет employer VIEWER. Явно описать read/create proposal/approve data/download полномочия. Клиент не может finalize, менять результаты комиссии, настройки номера и формы.

Проверки повторяются при каждом прямом чтении/записи, export, preview, file stream, event membership, history, restore, background job result. Composite FK/constraints или эквивалентная схема должны исключать cross-tenant связи даже при ошибке приложения. Центр A не создаёт assignment на Recipient B или групповой документ для чужого события.

Отзыв/смена роли/отключение membership отзывают соответствующие сессии и доступы. Смешанные группы фильтруются по разрешённым участникам, но исходный канонический документ не редактируется ради фильтра. Для полнофайловой выдачи нужна проверка разрешения на **весь** состав.

## 3. Приглашения и ссылки

Для портал-инвайта: криптографически случайный секрет, серверное хеширование, ограниченный срок, отзыв, одноразовый обмен на сессию либо эквивалентный безопасный flow. После обмена token убирается из URL, выставляются HttpOnly/Secure/SameSite cookies, не логируется исходный URL. Referrer-Policy и no-store, запрет индексации. Повторное/просроченное приглашение не открывает данные. Администратор вручную копирует ссылку — без обязательной внешней почтовой интеграции.

Короткая ссылка на согласование не даёт доступ ко всей компании. Состав и разрешение pin к конкретному заказу/редакции. Не хранить личные данные или bearer credentials в localStorage ради удобства. Публичный QR — отдельный тип токена и минимальный публичный контракт, не portal session.

Существующие Origin/CSRF, cookie/sessionVersion и throttling сохранить. Новые публичные endpoints имеют rate/size bounds и отдельные тесты, не «исключение из всей авторизации». Внешние URL не загружать сервером без специального allowlist/SSRF защиты; ручной файл достаточен.

## 4. Файлы и данные

Private storage и проверки hash/size сохраняются. Тип файла проверяется по содержимому и разрешённым форматам, не только имени; HTML/SVG/скрипты не исполняются. Для вложений дела и внешних документов — ограниченные MIME, лимиты, безопасное скачивание, quarantine/unverified при необходимости. ZIP traversal, archive bombs, XML entities, external references и Excel formulas не должны выполняться.

ФИО, табельные номера и BIN нужны только по фактическому процессу. ИИН/сканы личности/биометрия не добавляются «на всякий случай». Логи хранят ID/код/корреляцию, не полные списки, подписи, токены и raw uploads. Источник импорта хранится по согласованной политике, не дублируется бесконтрольно.

Размещение ПД, файлов, backup и внешние передачи требуют проверки требований Казахстана и соглашений до реального внедрения. Настройка «сервер в Казахстане» не является доказательством полной законности всех операций. Пакет не выполняет deployment и не даёт юридическое заключение.

## 5. Миграции

Не редактировать применённые миграции 001–005 и не выполнять db push/reset/destructive seed. Новые миграции — аддитивные, с явным контрактом версии и backfill только необходимых связей. Сначала nullable/additive, затем проверяемая миграция и constraints; не присваивать recipientId старым людям только по совпадению ФИО. Неизвестная связь остаётся legacy/unresolved с процедурой сверки.

Тесты: чистая установка; обновление базы со старыми individual выпусками; старые файлы/hash; разные номера и PS registration; partial drafts; old snapshots; откат приложения без удаления новых документов. Новые обязательные поля не должны делать старые оформленные данные нечитабельными. DB immutable triggers и tenant FK не отключаются ради backfill.

Для group владельца обеспечить проверяемые constraints и индексы. Для повторных потребностей/заказов/подтверждений добавить unique keys на семантические операции, а не надеяться на кнопку disabled. Финансовые записи и handover events не вписывать в immutable snapshots задним числом: новые события хранятся отдельно со ссылкой.

## 6. Очередь, preflight, нагрузка

Сохранить PostgreSQL очередь, lease, fencing, heartbeat, ограниченные retries и DOCX→PDF dependency. Новые режимы/типы заданий должны корректно ждать зависимости, переживать restart и не публиковать устаревший результат. Рендер не блокирует транзакцию; большие exports/packs при необходимости выполняются той же устойчивой очередью.

Пересмотреть `persistItems` full replacement и synchronous preflight только на основе измерений. Не объявлять их дефектами по названию и не удалять проверку геометрии ради скорости. Исследовать N+1, объём JSON, число запросов и память браузера на 100 строках. Не повышать лимиты без нагрузочного теста и понятного сообщения о превышении.

## 7. Backup, restore, экспорт и удаление

Backup включает БД, templates, оригиналы/восстановления, внешние вложения, новые связи и pinned versions; snapshot должен быть согласованным. Восстановление тестируется в другой disposable БД/каталоге. GC не удаляет канонические, активные, backup-pinned файлы и новые attachments из-за отсутствия обновлённого списка ссылок.

Полный tenant export содержит понятные связи людей/заявок/событий/документов/версий и файлов, без чужих записей. Экспорт работодателя — другой, более узкий. Политики архивирования/удаления и прекращения подписки не удаляют issued историю молча и не меняют статус документов на revoked по отсутствию оплаты.

## 8. Команды и среда

Использовать текущие package scripts и lockfile, не устаревшие команды родительского DSJ. В README текущего продукта setup вызывается `pnpm run setup`. Подготовка тестовых БД и переменных выполняется в отдельной среде. Интеграционные тесты допускают только `demo_test*`; не обходить этот guard.

В итоговых доказательствах указать фактические версии Node/pnpm/PostgreSQL/Python/LibreOffice/Word и hash форм. Официальные или зафиксированные runtime pins нельзя заменять предполагаемыми доступными версиями и сохранять старую отметку PASS. Недоступный Word или физический принтер — отдельный внешний пункт, не повод симулировать проверку и не повод прекращать всё остальное.

Production deploy, переключение, миграция реальной базы, реальные рассылки и публикация ПД не разрешены этим пакетом. Готовятся инструкция, совместимые изменения и локально проверенная поставка. Push/merge — только в пределах отдельного разрешения пользователя/среды.
