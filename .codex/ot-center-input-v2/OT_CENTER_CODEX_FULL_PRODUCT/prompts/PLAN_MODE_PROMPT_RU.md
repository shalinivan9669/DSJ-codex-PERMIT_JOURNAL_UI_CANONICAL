# Промпт для предварительного Plan mode

Изучи приложенный пакет OT_CENTER_CODEX_FULL_PRODUCT и живой репозиторий `shalinivan9669/DSJ-codex-PERMIT_JOURNAL_UI_CANONICAL`, ветку `codex/demo-print-2-0`, продукт `dsj2/products/demo/`. Audit SHA: `d1d377b641b0ee3e171c794e654b382d4d3af7c4`.

Это режим подготовки плана, не отдельный урезанный проект. Спланируй полную реализацию F01–F32 без P0/P1/P2, релизных отсрочек и исключения сложных пунктов. Главная цель — полезность для бизнеса учебного центра и удобство ежедневных задач оператора, руководителя и заказчика. Массовое оформление — одна из возможностей, а 100 человек — только параметр G1/G2. Прочитай `spec/00_BUSINESS_VALUE_AND_ACCEPTANCE_RU.md`, `spec/BUSINESS_VALUE_MAP.json` и V01–V12. Прочитай `01_CODEX_START_PROMPT_RU.md`, аудит, все спецификации, fixtures и новую приёмку. Сверь actual HEAD и исходники; исправь только устаревшие технические наблюдения, а не продуктовую цель.

В плане обязательно:

1. Фактическая карта существующих компонентов, схемы и методов, сохраняемые инварианты.
2. Полная матрица F01–F32: изменение UI, backend, данных, рендера, прав, тестов.
3. Одна целевая модель общих данных, индивидуальных исключений, группового протокола и привязки к постоянному человеку. Не предлагай несколько несогласованных моделей без выбора.
4. Внутренний порядок работ по зависимостям, не по коммерческим очередям; migration/compatibility plan до массового изменения кода.
5. Версионирование contract/snapshot и безопасное расширение ownership для group documents; сохранение одиночного сценария.
6. Явные allowlist и отдельный внешний доступ без возврата legacy DSJ.
7. Тесты на каждый инвариант, команды реального workspace, визуальную приёмку, V01–V12 и оба нагрузочных G1/G2, измерение повторного ввода и внешней ручной работы, времени действия отдельно от ожидания.
8. Критерий полного завершения с AT001–AT184 и проверкой полезности, фактические внешние блокеры и способ сохранить прогресс при лимите среды. Не выдавай неподтверждённые правовые сведения за готовую конфигурацию.

План должен показывать, как функция завершает конкретную задачу, а не только какой CRUD появится. Один человек не обязан проходить корпоративный мастер; управленческий обзор не требует второй ручной таблицы; клиент может работать через файлы без кабинета. Не создавай новые крупные модули ради этой рамки.

Не оценивай неизвестные задачи в обещаниях часов/дней. Не запрашивай у пользователя информацию, доступную в коде. По обратимым инженерным вопросам выбери обоснованный вариант. По юридическим и production-доступам сохраняй безопасные ограничения.

Результат: `Plan.md`, `Decisions.md`, матрица покрытия и точные условия реализации. Для перехода в выполнение используется основной `01_CODEX_START_PROMPT_RU.md`; сам Plan mode не обозначай выполненной реализацией.
