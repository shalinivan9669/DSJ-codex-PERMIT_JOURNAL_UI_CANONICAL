Шаблон для исполнителя. Заполнить после проверки репозитория, не считать выполненным.

Repo / branch / исходный SHA / фактический HEAD / git status / рабочая директория / прочитанные AGENTS / разрешённая область / команды запуска / имя disposable test DB.

## Порядок инженерных действий

Составить конкретные операции по зависимостям, а не приоритетный backlog: baseline → согласованный контракт → миграции/resolver → сквозные действия → полная проверка. Для каждого действия указать файлы, критерий и команду. Все F01–F32 остаются в одной поставке. После составления плана в основной задаче немедленно продолжить реализацию.

## Риски и решения

Связь группового IssuedDocument с несколькими заказами; сохранение v1; права работодателя; дата/правило; частичная регистрация; template versions; неизменность originals; backup новых вложений. Для каждого нужен ADR в Decisions, а не догадка, повторно принимаемая каждым агентом.

## Проверки

Baseline прежних тестов, тесты изменений, G1/G2, AT001–AT184, реальные формы, две компании/tenant, миграции, повтор и сбой. Невыполненный тест остаётся NOT_RUN; недоступная внешняя проверка записывается точно и не скрывает незавершённую разработку.

## Карта бизнес-пользы

Прочитать спецификацию 00 и связать BV01–BV08 с F01–F32. Для каждого V01–V12 записать исходные сведения, удаляемую ручную работу, результат, путь в UI, нужные тесты и зависимость от уже существующего кода. Не сводить план к полям БД или одной массовой форме.

Приёмка: AT001–AT184, V01–V12 и G1/G2. Маленькие сценарии равноправны с массовыми. Не создавать обязательные действия для оператора только ради отчётности руководителя.
