# Аудит исходной ветки: факты, ограничения и точки изменений

Репозиторий и commit — `REPO_LOCK.json`. Ссылки на конкретные версии файлов — `SOURCE_MAP.json`. Это целевой **статический аудит** ключевых исходников и контрактов. Не полный security audit репозитория; не запуск приложения и не проверка production.

## 1. Какое приложение найдено

Ветка `codex/demo-print-2-0` содержит автономный продукт в `dsj2/products/demo/`. Root/parent/local AGENTS ограничивают его печатным контуром и запрещают импорт старой DSJ-логики. В реальном package.json указан pnpm 11.27.1; точные runtime pins необходимо сверять по действующей поставке, а не по старому ACCEPTANCE_RU.md. Root `dsj2` и autonomous workspace имеют разные назначения.

Основной путь — `/requests`, редактор заявки, `/customers`, история и настройки. Серверный `PrintRequest` содержит JSON-черновик и revision, `RequestItem` — строки. `Issuance` и `IssuedDocument` фиксируют выпуск; старых концептуальных CompanyWorkspace/PrintRecord здесь не следует создавать повторно.

## 3. Конкретные ограничения и изменения

### A. Массовое редактирование слишком узкое

`apps/web/components/editor.tsx`, BulkDialog: доступны только `documentDate`, `trainingSubject`, `result`. Patch применяется ко всем assignments выбранных людей. Нет выбора только определённого направления в этом обработчике, полноценного diff, fill-empty policy или массового добавления набора. Именно здесь нужно убрать необходимость заходить в каждый assignment.

### B. Один imported row получает одно назначение

`apps/web/lib/imports.ts`, mapImportRow: выбран один templateId, `assignments: [assignment]`. Полезно сохранить это как совместимый путь, но добавить назначение нескольких услуг/форм по пресету и сопоставлению колонок без повторного импорта людей.

### C. Групповые протоколы не являются текущей бизнес-моделью

assignmentSchema допускает `INDIVIDUAL` и `EXTERNAL_REFERENCE`. finalize перебирает item × assignment, резервирует номер и создаёт snapshot с `items: [renderedItem]`. Существующий протокол связан с документом **того же item**. Исторический A37 прямо сообщает, что GROUP отвергается. Слияние PDF не исправит эту модель: нужен один групповой выпуск и членство участников.

### D. Постоянный человек не связан с заявкой явно

Recipient есть в Prisma и CRUD; itemSchema содержит локальный id/importId/sourceRow, но не явный persistent recipientId. Импортный id строится из import batch и строки. Это не идентичность человека между заказами. Добавить явную связь без слияния по имени и сохранить исторические снимки.

### E. Повтор того же файла и обновление списка — разные операции

applyImport возвращает прежний состав, если importId уже присутствует, иначе добавляет строки. Это хорошая защита от повтора, но не update/diff между изменёнными файлами. Для обновления нужен отдельный reconciliation flow, revisions и явные решения по исключениям.

### F. Метаданные работодателя смешаны с заказчиком как fallback

employerFields использует данные выбранного customer, если поля item пусты. Полезный fallback, но для плательщика, посредника, смены работодателя и смешанных групп недостаточен. Добавить явный employer/engagement scope; не переписывать существующие snapshots.

### G. Статически найдено расхождение BIOT ITR в registryExport

requests.ts различает `biot-itr-protocol` и `biot-protocol` через protocolTemplateFor. files.ts в registryExport строит `${family}-protocol`, что для ITR даёт `biot-protocol`. При отсутствии внешнего номера возможна потеря/неверная связь номера в XLSX. Это конкретная проверяемая гипотеза дефекта, не выполненное runtime-воспроизведение. Написать тест с worker и ITR в одной заявке, затем унифицировать resolver для snapshot/export/preview.

### H. База больше 100 записей

Editor загружает `/customers?page=1&pageSize=100` и строит select только из этого ответа. GET recipients возвращает take:100 без поиска/страниц и total:items.length. Не путать лимит **100 людей в заявке** с размером всей базы. Нужны server-side search/pagination и доступ к уже выбранной записи вне первой страницы.

### I. Общий профиль выбирается заново; наследование надо сделать явным

Profile versions и snapshot уже защищают выпуск. Новый scope заявки/события должен показывать выбранную версию, изменения и исключения, а не подменять всё последним profile незаметно. Устаревшее подтверждение списка/preview должно инвалидироваться по relevant hash.

### J. Имена файлов технические

queue.ts создаёт имя `templateId-documentId.ext`, files.ts — `DEMO-registry.xlsx` / `DEMO-complete.zip`. Нужны безопасные client-facing имена, порядок и структура выдачи, не изменяя исходные immutable bytes.

### K. Массовый ввод нуждается в измерении, не в догадке

На каждое сохранение persistItems удаляет и создаёт строки запроса заново; Editor отправляет полный draft после debounce. Это кандидат на измерение DB/network/render нагрузки при 100×10. Само по себе не доказанный performance bug. Оптимизировать по профилю, сохранив атомарность и revision conflict.

## 4. Чего в просмотренной модели/маршрутах не найдено как законченного процесса

Настоящие event/group protocols, импорт-diff, customer output preferences, постоянная employment history, order obligations/delivery, renewal worklist, employer portal с customer scope, external evidence registry, service/rule passports и небольшой финансовый слой. Статус: **целевая доработка / не найдено в обследованных поверхностях**, не универсальное доказательство отсутствия любых похожих строк во всём Git.

## 5. Важная поправка к наследуемой документации

В начале актуального `docs/ACCEPTANCE_RU.md` указано: после последних BIOT-изменений ограниченная проверка выполнена, полная коммерческая приёмка не завершена. Текст ниже содержит исторические environment versions и PASS старого состояния. Идентификаторы 11 форм и текущие версии брать из contracts/manifest, команды — из package.json. RegulatoryReview в template manifest — метаданные репозитория, не независимое юридическое заключение данного аудита.

## 6. Вывод для исполнителя

Не начинать с переписывания рендера, БД, auth или нового UI framework. Сохранить существующий фундамент. Основное расширение — централизованное разрешение общих данных, массовые назначения, реальные групповое основание/протокол, постоянная идентичность, удобный вход/выход данных и связанные сервисные процессы. Все изменения должны пройти новую фактическую приёмку.
